## 2. 上下文与模块映射

### 2.1 统一语言（本闭环使用的术语）

沿用 PRODUCT"业务概念"表，补充 1a 实现中需要区分的四个词：

| 术语 | 含义 | 区别 |
| :--- | :--- | :--- |
| 扫描运行 | 一次"时间窗口 [from, to) × 表集合 × 规则集版本 × 指纹密钥"的执行，对应一个输出目录 | ≠ 重扫任务（PRODUCT 概念，是有发起人和原因的业务请求）；1a 没有任务登记，运行由人手工发起 |
| 断点（提交点） | 每张表已经可靠处理到的 `(ts, request_id)` 键位 | ≠ 检测进度（PRODUCT 概念，持续模式下需要处理迟到写入）；封闭窗口下两者等价 |
| 命中明细（hit） | 一个存储位置中的一条调用记录 × 一个凭证指纹 | ≠ 命中（PRODUCT 概念，按"位置"细到来源角色）；hit 把同一记录内同一指纹的多个角色、多次出现合并为一行 |
| 发现（finding） | 一次扫描运行内"主体（员工，无员工时为 Key）× 凭证指纹"的聚合 | ≠ 泄漏事件：发现没有处置状态，可随时从明细重算 |

### 2.2 逻辑模块 → 1a 实现单元

split 的方案 B 是逻辑模块，不要求一一对应服务或包。1a 部署为**一个 Go 命令行程序**（SRC-014 ⑤），子命令 `probe` / `scan` / `report`。

| 逻辑模块（PRODUCT 第 253–262 行） | 1a 实现单元 | 是否接触原文 | 说明 |
| :--- | :--- | :--- | :--- |
| `record-intake` | `internal/store`（读取、分页、大小上限）、`internal/extract`（来源角色拆分）、`main.go` 的 `scanTable`（批次、断点、限速） | 是（瞬时内存） | `probe` 子命令也在此单元，只输出统计 |
| `secret-detection` | `internal/rules`（规则与结构解析）、`internal/detect`（按角色识别、指纹、记录内去重、网关 Key 确认） | 是（瞬时内存） | 出口类型 `Hit` 没有原文字段 |
| `detection-ruleset` | `internal/rules` 中的类型表与 `Version` 常量 | 否 | 1a 只有内置规则集，没有发布 / 回滚 |
| `exposure-reporting` | `internal/output`（明细写入、覆盖、发现聚合、`summary.md`） | 否 | 从 `hits.csv` 与 `checkpoint.json` 派生 |
| `gateway-adapter` | `internal/store.LoadKeys` + `detect.confirmGatewayKey` | 否（只读 `key_hash`） | 与 split 的"不暴露哈希"契约有偏差，见 DES-009 与 [FB-004](./feedback.md) |
| `leak-incident`、`evidence-access`、`stock-remediation`、`channel-audit`、`leak-console` | 无 | — | 不在本轮范围 |

**原文边界在代码中的落点**：`rules.Match.Value` 是唯一携带原文的字段（`internal/rules/rules.go:28`，注释"只在内存中使用"）；`detect.Hit` 没有 `Value` 字段，`detect.Scan` 只把 `Fingerprint(m.Value)` 和 `m.Masked` 放进 `Hit`（`internal/detect/detect.go:170–180`）。输出层只能拿到 `Hit`，因此 BR-001 由类型结构保证，而不是靠输出层自觉过滤。

## 3. 模型与不变量

### 3.1 为什么本闭环不引入聚合

split 已判定本产品主体是数据流，事件处置才有状态（split-review S01、S06）。闭环 A 中：

- 没有多个写入方竞争同一份可变业务状态：一次扫描运行只有一个进程写一个输出目录。
- 识别是纯函数：`(记录内容, 规则集版本, 指纹密钥) → 命中明细集合`，没有副作用。
- 发现是派生结果，没有生命周期。

所以这里用"责任单元 + 不变量"表达，不强行建聚合（避免 D02 / G06）。第一个真正需要聚合的是阶段 1 的泄漏事件（主体 + 指纹，保护 BR-006 的唯一性），它依赖 DES-005 的指纹稳定性，放到阶段 1 设计时再做。

### 3.2 责任单元与它们保护的规则

| 责任单元 | 共同保护什么 | 不负责什么 | 行为 | 关联 BR |
| :--- | :--- | :--- | :--- | :--- |
| **识别函数**（`detect.Detector.Scan`） | ① 输出不含原文；② 相同输入产生相同结果（确定性，排序后输出）；③ 同一记录内同一指纹只产生一行 hit，多条规则命中同一值时按类型优先级取一个 | 跨记录合并；判断是否已处理过 | 按来源角色逐段识别 → 占位降级 → 成对确认 → 指纹 → 记录内合并 → 可选网关 Key 确认 | BR-001、BR-002、BR-003、BR-015（记录级） |
| **扫描运行**（`RunState` + 输出目录） | ① 一次运行只用一个规则集版本（续扫时版本不同就拒绝，`main.go:168`）；② 断点之前的记录其 hit 已提交；③ 每条读到的记录都计入覆盖统计且只计一次 | 跨运行合并；规则效果统计 | 按表键集分页 → 并行识别 → 串行写明细 → 刷盘 → 保存断点 | BR-005、BR-015、BR-016 |
| **凭证身份方案**（指纹规范化 + HMAC 密钥） | 同一凭证在不同记录、不同运行、不同规则集版本下得到相同指纹 | 判断凭证是否有效 | 规范化取值 → HMAC-SHA256 → 取前 32 位十六进制 | BR-001；是阶段 1 BR-006 合并的前提 |
| **发现与报告**（`output.BuildReport`） | 只从明细和覆盖统计派生，可重算；不含原文；覆盖缺口与发现一起给出 | 修改明细 | 过滤占位与第三层 → 按"主体 × 指纹"聚合 → 排序 → 写 `findings.csv`、`summary.md` | BR-001、BR-005 |

**不变量 ② "断点之前的记录其 hit 已提交" 当前没有被完整保护**：非正常退出时存在失败窗口，见 DES-007 与 RP-06。

### 3.3 身份

| 对象 | 身份 | 依据 |
| :--- | :--- | :--- |
| 调用记录 | `request_id`（两表都以其为主键，schema 第 2777、2785 行） | PRODUCT 业务概念"调用记录"（第 83 行） |

## 4. 一致性与协作

### 4.1 原子边界

| 边界 | 范围 | 如何保证 | 当前状态 |
| :--- | :--- | :--- | :--- |
| 一批记录的提交 | 一批 hit 写入 `hits.csv` 与断点推进 | 先 `Flush + Sync` 明细，再原子重命名写断点（`main.go:306–314`；`internal/output/output.go:199–210`） | **不是原子的**：两步之间崩溃会重复写入；见 DES-007 |
| 断点文件 | `checkpoint.json` | 写临时文件后 `rename` | 临时文件写入后没有 `fsync`，断电时可能得到空文件；见 DES-007 |
| 数据库读取 | 单条 `SELECT` | 只读会话 + 语句超时；每批一条语句，不跨批持有事务 | 已实现；不要求跨批一致快照，因为封闭窗口内的历史记录不再变化（前提：没有迟到写入，见 DES-011） |

### 4.2 并发

- **数据库侧**：始终单连接、串行分批读取（`main.go:274`），读取压力只由 `-batch`、`-sleep`、`-max-body`、`-stmt-timeout` 控制。
- **识别侧**：每批内用 worker 池并行执行识别函数（`main.go:282–298`）。识别是纯函数，结果按下标写回数组，写明细在主 goroutine 串行进行，因此不存在共享可变状态。
- **多进程**：两个 `scan -resume` 同时指向同一目录时没有互斥，会交错追加明细、互相覆盖断点。1a 是人工运行，发生概率低，但后果是明细损坏。detail 需要加目录锁（DES-007）。

### 4.3 协作契约（1a 实际形态）

| 发起方 → 接受方 | 形态 | 结果语义 | 失败 / 恢复责任 |
| :--- | :--- | :--- | :--- |
| `record-intake` → 网关库 | 外部只读 SQL | 返回一批记录；超限内容以 NULL + 超限标志返回 | 语句超时或连接中断：本批不提交，断点不动，`-resume` 从断点重读 |
| `record-intake` → `secret-detection` | 进程内函数调用 | 总是返回 `Outcome`（含解析失败标志），单条记录解析失败不影响其他记录 | 无外部副作用，无需补偿 |
| `secret-detection` → `gateway-adapter` | 进程内查询（内存中的哈希表） | 本网关 Key（本人 / 他人，启用 / 停用）/ 不是或无法确认 / 哈希方式未知 | 无法确认时保持 `llm_api_key_generic`，不外发（BR-002） |
| `secret-detection` → `exposure-reporting` | 追加写 `hits.csv` | 已刷盘即视为已提交（当前）；目标是"断点记录的偏移之前才算已提交"（DES-007） | 扫描运行负责 |
| `exposure-reporting` → 安全团队 | 本地文件（0600） | 报告标明窗口、完成时间、覆盖缺口 | 人工分发；收件人待 Q-015 |

## 6. 设计决定

验证状态取值：**已实现并验证（合成数据）**＝有代码与运行过的单元 / e2e 证据；**已实现、未验证** ＝有代码无运行证据；**反例已确认（代码审读）** ＝读代码确认存在问题，未运行复现；**候选** ＝未实现或依赖未取得的外部证据。

| DES | BR / 交接依据 | 设计选择与理由 | 所有者 / 责任单元 | 原子边界与跨边界协调 | 外部前提及证据 | 验证状态 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |

### 9.3 回看条件

- `probe` 显示两表内容不同且各有独有内容：DES-006 的"只扫一张表"建议失效，改为两表都扫并以位置区分治理范围。
