# LLM 网关凭证泄漏防护：独立 v2 产品定义

> 本文是独立产品与拆分方案，不作为现有 xflow 的正式阶段或实施基线。产品内容由 `/xf-product-v2` 维护，模块结构由 `/xf-split-v2` 维护。

## 产品概述

公司员工和编码 agent 通过内部 LLM 网关使用大模型。2026 年 9 月公开的两件事说明，发给模型的内容本身就是高价值数据：一位研究者称，他从中转站中间商那里买到用户对话数据，里面的 SSH 密钥、VPN 配置、阿里云密钥和 GitLab 令牌足以接管多家机构（SRC-004，未核实）；Anthropic 的报告也记录了中转站和模型厂商保存、转卖、二次转发用户对话的行为，被转出去的内容里有员工贴进去的在用凭证和内部代码（SRC-006）。

我们的网关处在和"中转站"相同的位置：它能看到员工请求的明文，而且表结构里就有保存请求头、请求体和响应体的字段（SRC-008；是否实际写入待 Q-002 核实）。本产品要解决三件事：

1. **发现**：网关已保存的调用内容里，员工或 agent 发出（或模型返回）了敏感凭证时，能及时识别出来。凭证类型必须覆盖 SSH 密钥、VPN 配置、阿里云密钥、GitLab 令牌等（SRC-001）。
2. **闭环**：通知到人，推动凭证轮换，能区分误报，留下处置记录，并定期出报告。
3. **不让网关自己成为泄漏源**：检测结果不保存凭证原文；网关已经落库的历史内容也要能被找出来并治理。

**接入方式（1.1 起）**：本产品**旁路读取网关数据库**中已保存的调用记录，不嵌入网关的请求处理链路（SRC-012）。这带来三个直接后果：
- 能检测的范围等于网关实际保存下来的内容；没保存的调用看不到，必须在覆盖报告里明确显示。
- 发现有延迟，只能事后通知，不能在请求发往上游之前脱敏或拦截。
- 检测器本身要读取网关库里的原文，它的访问权限和网关库一样敏感。

**怎么判断有用**：
- 用植入的测试凭证验证，每个首批类型都能被识别到正确类型，事件能走完"通知 → 轮换确认或误报关闭"的流程。
- 检测和告警产生的所有记录里都查不到凭证原文。
- 安全负责人能说清楚：网关落库内容里有多少类、多少个疑似凭证暴露，涉及哪些部门，还有哪些调用没被检测以及原因。

**本产品覆盖不了的部分**：员工绕开网关、私下使用外部中转站（案例库路径 P-B）。这正是推文里描述的主要场景，但网关里看不到，列入产品边界和 Q-007。

## 目标用户

| 用户角色 | 使用情境与困难 | 核心诉求 |
| :--- | :--- | :--- |
| 安全运营分析员 | 事件发生后才知道凭证泄露；网关日志量大，靠人工翻内容不现实；翻内容本身又会接触到凭证原文 | 只看到脱敏后的命中信息就能判断真假；能按严重程度排队处理；能追踪到轮换完成 |
| 安全负责人 | 需要回答"我们员工有没有类似行为、暴露了多少、检测覆盖了多少"；要决定规则集是否上线 | 暴露面和覆盖率报告；规则上线前有评估依据 |
| 员工（请求发起人 / Key 持有人） | 调试时顺手贴了配置，或 agent 自动读了 `.env`，自己并不知道凭证已经发出去 | 尽快收到清楚的提醒，知道要轮换什么；误报时能申诉；不因为误报被反复打扰 |
| 网关管理员 | 维护上游渠道、日志留存和网关数据库；渠道接入地址是否可信没有持续核对；历史日志里可能有大量凭证 | 检测器读库不影响在线服务；能核对上游接入地址；能安全治理存量日志，同时不破坏计费和审计 |
| 规则维护人（安全团队） | 新的凭证格式不断出现；规则写宽了误报多，写窄了会漏报 | 规则有样本、可评估、可回滚，能看到每条规则的命中和误报情况 |
| 法务 / HR / 合规 | 检查员工对话内容属于员工监控，需要制度依据和告知 | 上线前能审查检测范围、数据留存方式和查看权限；事后能审计谁看过什么 |

| :--- | :--- | :--- | :--- | :--- |
| 调用记录（外部事实） | 网关保存的一次模型调用，由网关的请求标识确定身份，带调用发生时间、调用人、Key、部门和保存的内容 | ≠ 检测结果：调用记录归网关所有，本产品只读；同一次调用的内容可能保存在网关库的多个位置 | 本产品不修改（经批准的存量治理除外，见 BR-011）；可能按网关保留期被删除 | SRC-008、SRC-012 |
| 检测进度与覆盖（观测） | 已经可靠检测到哪个时间点，哪些调用没检测以及原因 | ≠ 调用记录数量：进度推进到某个时间点，不代表该时间点之前的记录都已写入并被读到 | 需要保留补扫和重扫的历史 | SRC-012 |
| 重扫任务 | 对某个时间范围、使用某个规则集版本重新检测的请求，来源是回扫、规则更新或补扫 | ≠ 日常增量检测：重扫可能读到早已处理过的记录，结果要与已有命中合并 | 有发起人、原因、范围和完成情况 | SCN-006、012、013 |
| 敏感凭证类型（主数据） | 一种需要识别的凭证或敏感数据，如"SSH 私钥""阿里云 AccessKey 对"。有稳定类型标识、危害等级、识别特征说明和处置指引 | ≠ 检测规则：类型是业务定义，规则是识别它的手段，一个类型可以有多条规则 | 需要版本；事件保留当时的类型版本 | SRC-001、SRC-003 |
| 规则与规则集版本（配置意图） | 规则：识别某个类型的一种方法及其正负样本；规则集版本：一次发布生效的全部规则（含模型辅助手段）及其启用状态 | ≠ 类型目录；≠ 豁免：规则决定"认不认得出"，豁免决定"认出来之后要不要通知" | 版本只追加，不修改；可以回滚到旧版本（回滚即重新发布旧内容）；命中保留识别时的版本 | SRC-009、SRC-010 |
| 命中（观测） | 某次调用中，在某个来源角色的位置识别出的一处疑似凭证 | ≠ 泄漏事件：一个事件可以包含很多命中；命中本身不代表已确认泄漏 | 只追加，不修改；保留识别时间、调用发生时间和规则集版本 | SRC-005 |
| 调用发生时间 与 发现时间 | 调用发生时间：员工实际发出内容的时间；发现时间：检测器识别出来的时间 | 两者可能相差很久（补扫、回扫、重扫）；判断"是不是关闭后的新泄漏"必须看调用发生时间 | 两个时间都随命中保存 | SRC-012；SCN-012、013 |
| 来源角色（观测属性） | 命中出现在哪里：用户输入、系统提示、工具结果、请求头、模型输出 | 用户输入 ≠ 工具结果：前者是员工主动贴的，后者是 agent 读出来的，整改对象不同；模型输出指向的是网关侧或上游侧密钥被套出 | 随命中保存 | SRC-003 P-A/P-E、SRC-006 |
| 凭证指纹（身份） | 由凭证值推导出、无法还原的标识，用于判断"是不是同一个凭证" | ≠ 脱敏展示片段（如前 4 后 4）：指纹用于比对，片段用于人工辨认；两者都不能还原原文 | 同一凭证在不同时间得到相同指纹 | SRC-003 §6 |
| 泄漏事件（派生 + 处置状态） | 同一主体（员工或 Key）+ 同一凭证指纹的聚合，是通知、研判和关闭的对象 | 研判结论（真实 / 测试 / 误报）≠ 处置状态（待通知 / 待轮换 / 已关闭），两者分开记录 | 状态变化需要完整历史：谁在什么时间以什么依据改动 | SRC-003 |
| 凭证归属与轮换责任人 | 能够轮换这个凭证的人：员工本人、云账号管理员、GitLab 管理员或网关管理员 | ≠ 请求发起人：员工贴出的凭证可能不归他管；模型输出类事件的责任人是网关管理员 | 事件上可以改派，并保留改派记录 | SCN-001、003、005 |
| 豁免（有期限的承诺） | 在某范围和期限内，特定凭证或类型的命中不通知 | ≠ 误报结论：误报是事后判断，豁免是事先授权 | 必须有到期时间；到期自动失效；按调用发生时间判断是否在豁免期内 | 本次建议 |
| 证据查看授权 | 某人为某事由、在一段时间内查看某事件原始上下文的许可 | ≠ 管理员角色：管理员身份不等于自动能看原文 | 每次查看都审计 | SRC-003 §6 |
| 授权上游清单（配置意图）与渠道实际接入地址（现状） | 清单：允许网关把流量发往的上游地址；现状：渠道当前配置的地址 | 两者不一致才是风险；"官方厂商"也不等于内容不会被二次转发 | 清单变更要有记录 | SRC-003 P-C、SRC-006 |
| 治理计划与执行结果 | 计划：经批准要脱敏或清理的存量范围；执行结果：网关侧实际完成的情况，以复扫核验为准 | 计划批准 ≠ 已治理：执行由网关侧完成，结果要复扫确认 | 保留审批、执行和核验记录 | SRC-008 |
| 暴露态势与报告（派生结果） | 按维度汇总的事件、处置和覆盖统计，以及按周期生成的报告 | 只能从事件、命中和检测进度计算，不能手工维护；报告是某个截止时间的快照 | 能按历史时间段重算；报告保留截止时间 | SRC-002 |

## 产品边界

### 做什么

- 旁路读取网关数据库中已保存的调用记录，检测其中的用户输入、系统提示、工具结果、请求头、模型输出（路径 P-A、P-E，以及模型输出方向的密钥外泄）。
- 按附录 A 的类型目录和受管理的规则集识别敏感凭证，首批覆盖 SSH 密钥、VPN 配置、阿里云密钥、GitLab 令牌及同类高危凭证。
- 检测进度、补扫、重扫和覆盖统计，确保不漏、不重。
- 事件的通知、研判、关闭和审计闭环；员工自助确认轮换或申诉。
- 周期暴露报告、回扫暴露报告、检测覆盖报告。
- 网关自身落库内容的凭证暴露统计与治理（SCN-006）。
- 上游渠道接入地址的授权核对（路径 P-C）。
- **优先复用**网关已有的能力，不重新建设：Key 来源指纹与用量基线（CAP-011 直接复用）；组织与员工主管关系、操作审计、告警与通知投递、报告快照（评估后复用）。现有的"异常待确认与复核"流程针对的是用量和费用异常，只能参考其状态设计（依据见 SRC-008）。

### 不做什么

- **员工绕开网关、私用外部中转站（路径 P-B）**：网关里看不到，需要出口代理、DNS 或终端侧手段，归属待 Q-007。本产品不声称覆盖这一路径。
- **发出前脱敏或拦截（CAP-008、SCN-007、BR-008）**：1.1 起旁路读库，做不到。以后如果嵌入网关，要重新定义。
- 检测网关没有保存的调用内容（BR-005）。
- 用疑似凭证在线验证第三方系统中的有效性（BR-002）。
- 本版不自动吊销外部系统（阿里云 RAM、GitLab 等）中的凭证，只做通知和确认，是否联动待 Q-005。
- 不对员工做绩效或纪律性评价，也不输出"员工风险画像"之类的结论；处分决定不在本产品内。
- 本版不对员工推送个人信息（身份证、手机号等）和内部机密业务内容（财务预测、未公开产品规格等）的检测结论；模型辅助识别在本版只做影子运行和评估（附录 A 第三层）。
- 不检测上游响应是否被篡改（路径 P-F）。前提是网关直连可信上游；转发型渠道的风险由 CAP-010 暴露出来。
- 不做"大量套取推理过程"之类的滥用调用检测。
- 不直接改写网关数据库：存量治理由网关侧按批准的计划执行（BR-011）。
- LiteLLM 投毒自查、首次渠道盘点这类一次性运维动作不算产品能力，列在交付优先级的阶段 0。

**划分的首要原则：原文边界。** 只有三个模块会接触凭证原文：`record-intake`（读取）、`secret-detection`（识别）、`evidence-access`（授权查看）。其余模块只处理指纹、脱敏片段和调用标识。这条边界直接落实 BR-001，也把高敏访问权限限制在最少的模块里。

**输入通道不改变这条边界。** 阶段 1a 的实现除了只读网关库，还支持扫描本地导出文件（每行一个请求体）。两种输入都只进入 `record-intake`，识别、聚合、报告的职责和契约完全相同；差别只在可得的事实：导出文件没有员工、部门、客户端和时间，也无法与 `api_keys` 比对，因而覆盖口径和主体判定不同（见"核心对象所有权"）。是否把导出文件作为受支持的产品输入，待 product 确认（FB-018）。

### 划分依据与方案取舍

| 方案 | 划分方式 | 优点 | 代价与风险 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| A：三个粗模块 | 扫描管线（读取 + 识别 + 回扫）/ 处置与报告（事件、通知、证据查看、报告、治理）/ 规则与配置 | 模块间接口少，最快做出第一版 | 证据回溯要读原文，放进"处置与报告"后，原文会进入本应只处理脱敏数据的模块；网关表结构变化和规则变化都要改扫描管线；存量治理的审批和执行核验混在处置里 | 不建议 |
| **B：按原文边界、权威、变化原因细分（建议）** | 10 个逻辑模块（见模块列表），原文只出现在 3 个模块中 | BR-001 有结构保证；网关表结构变化只影响 `record-intake` 和 `gateway-adapter`；规则变化只影响 `detection-ruleset` 和 `secret-detection`；报告可重算且没有写权限 | 模块间契约多，需要把命中、事件、进度的契约定清楚 | **建议采用**。逻辑模块不等于微服务，可部署为一个服务加检测处理进程 |
| C：写回网关库，做成网关的子域 | 事件和报告写进网关数据库，直接复用网关的通知发件箱、报告快照、异常复核表 | 复用最多，网关现有界面可以直接展示 | 泄漏事件语义由网关团队和安全团队共同写入同一批表；高敏的检测元数据和普通运营数据同库同权限；检测发布和网关发布绑在一起 | 不建议作为默认方案，待 Q-014；可以只复用网关通知投递，通过适配接口调用 |

核心域候选：`secret-detection` 和 `leak-incident`，承载"认得准"和"闭环"两个差异化价值。`detection-ruleset`、`record-intake`、`exposure-reporting`、`stock-remediation` 是支撑域；`gateway-adapter`、`evidence-access`、`leak-console`、`channel-audit` 提供通用或周边能力。这是产品战略建议。
