对 `/xf/analyze` 审计发现的问题进行深度分析并修订设计文档。

## 用户输入

```
$ARGUMENTS
```

**参数解析**：

- **必填**：问题编号或问题描述（如 `[高] spec:183 验收标准矛盾` 或 `CA-03`）
- **可选**：模块名前缀（如 `001`），用于限定分析范围

从 `$ARGUMENTS` 中提取问题标识。匹配规则：
1. 方括号标记的优先级+位置（如 `[高] 002 spec.md:183`）
2. 编号引用（如 `CA-03`、`D-11`）
3. 自由文本关键词——在审计报告（`docs/analyze/` 目录）中搜索匹配

如未指定模块，从问题涉及的位置自动推断。

## 前置条件

- `xspec/constitution.md` 必须存在
- 审计报告已存在（`docs/analyze/` 目录下有对应文件）
- 目标模块的设计文档已完成（design.md / data-model.md 存在）

---

## 步骤 1：精准诊断

**目标**：不信任审计报告的表面描述，回到源文档定位矛盾的本质。

1. 读取审计报告中该问题的描述
2. 对问题涉及的所有文件执行 grep/read，找到所有相关位置
3. 区分问题本质——属于以下哪一类：

| 类别 | 说明 | 典型修复 |
|:---|:---|:---|
| 措辞错误 | 某份文档写了错误的语义 | 修改措辞 |
| 类型声明不一致 | 跨文档/跨模块的类型定义矛盾 | 统一类型 |
| 跨模块数据格式不兼容 | 同一数据在存储格式间（ZON/JSON/SQLite）的表示差异 | 统一格式 + 验证序列化/反序列化链路 |
| 设计缺陷 | 某个场景未被任何文档覆盖 | 补充设计 |
| 功能缺失 | 需求有但设计无 | 补充设计+AC |
| 职责越界 | 模块承担了不应承担的职责 | 划清边界 |

4. 输出：**问题的精确陈述**（1-2 句，说清什么和什么矛盾，矛盾的本质是什么）

---

## 步骤 2：多方案生成

**目标**：穷举可行方案，不做预设排除。

1. 列出所有可行方案（≥2 个），每个方案包含：
   - 做法描述
   - 涉及哪些文件的哪些位置
   - 优势
   - 劣势
   - 风险等级（低/中/高）

2. **必须包含"最小变更"方案**——只改最少文件/最少行数的修复方式

3. **必须包含"不做"方案**——如果合理的话，解释为什么可以不修

4. 输出对比矩阵表

---

## 步骤 3：过度设计审查

**目标**：过滤掉为理论风险加运行时机制的方案。

对每个方案逐项追问：

| 检查项 | 说明 |
|:---|:---|
| 真实风险 vs 理论风险 | 这个机制解决的是 P0 约束下会真实发生的风险，还是理论上可能但几乎不会发生的风险？ |
| P0 场景可行性 | 在 P0 约束（单线程、人工触发、小规模知识库 < 300 条）下，这个场景真的会发生吗？ |
| 现有机制覆盖 | lint / CLI 命令 / 日志 / pending.json 是否已经能发现/处理这个问题？ |
| 最坏后果 | 如果什么都不做，最坏情况是什么？用户能否自行处理？ |
| 宪章原则五 | "不得在当前规模不需要时提前引入技术方案"——方案是否违反？ |

**判定规则**：
- 如果方案解决的问题在 P0 约束下几乎不会发生 → **过度设计，排除**
- 如果方案引入的新机制比原始问题更复杂 → **过度设计，排除**
- 如果方案引入多项增强，单项不复杂但叠加后总复杂度超过原始问题 → **过度设计，排除**（复杂度递归陷阱）
- 如果方案只是修改文档措辞/类型声明，不引入新机制 → **不是过度设计，通过**
- 如果方案解决的问题是真实存在的数据丢失/功能断裂 → **不是过度设计，通过**
- 如果最坏后果严重但发生概率极低（如进程崩溃+特定时序），且现有机制已能发现 → **倾向不做，通过审查时需标注风险**

输出：每个方案是否通过过度设计审查，及理由。

---

## 步骤 4：技术验证

**目标**：确认方案的技术前提成立。

如果方案依赖特定技术前提，必须查证：

| 依赖类型 | 查证方式 |
|:---|:---|
| 标准库 API 行为 | 读取 Zig 标准库源码（`std.zon.stringify`、`std.json` 等） |
| 第三方库行为 | 读取 `research/` 目录下的研究报告 |
| 格式规范 | 读取 ZON/TOML/JSON 规范文档 |
| 编译器特性 | 读取 Zig 0.16 release notes 或源码 |

如技术前提不成立，降级方案或补充替代方案。

输出：技术前提是否成立。

---

## 步骤 5：最小执行

**目标**：选择通过审查的最低总成本方案，精确修改文件。

### 5.1 方案选择规则

选择通过过度设计审查且技术前提成立的方案，按以下优先级决策：

**1. 彻底性**：优先选择完全消除矛盾的方案——所有涉及位置均一致，无残留隐式映射。

如果方案留有残余，评估残余维护成本：

| 残余性质 | 残余维护成本 | 处理方式 |
|:---|:---:|:---|
| 信息不一致（文档间措辞/值域不同） | 高 | 必须彻底——残余必然导致实现者误解 |
| 设计歧义（两种解读都合法但行为不同） | 高 | 必须彻底——实现者可能选错解读 |
| 冗余但无害（幂等调用、冗余字段） | 低 | 可接受——加注释说明即可 |

**2. 简洁性**：在可接受的彻底性水平中，优先不引入新概念/新机制的方案。

**3. 最小改动**：在简洁性相同时，优先修改量最少的方案。

**复杂度计算**：

- 同质修改（同一措辞/类型修正的 N 次重复应用）不计入复杂度——例如将 7 处 "L1+L2+L3" 统一为 "L1+L2+L3+pending.json"，复杂度为 1 而非 7
- 跨模块修改的异质成本 +1（模块边界增加协调成本）
- 单模块内结构变更（如状态机修改）的异质成本 +1

**决策公式**：

```
总成本 = 异质修改处数 + 残余维护成本

选择总成本最低的方案。
```

**不确定时的决策**：

以下情况视为不确定，不应单方面推荐，应向用户呈现选项让用户决策：

| 不确定场景 | 说明 | 呈现方式 |
|:---|:---|:---|
| 总成本持平 | 两个方案总成本相同或差值 ≤ 1 | 列出候选方案 + 各自优劣，推荐其一但标注"可选" |
| 残余性质判定模糊 | 残余介于"信息不一致"和"冗余但无害"之间 | 列出两种判定的结论差异，让用户选择彻底程度 |
| 跨模块影响不可预判 | 修改涉及 001+002 两个模块，对 001 的副作用不确定 | 列出修改范围 + 风险假设，让用户确认是否跨模块修改 |
| 设计方向二选一 | 两种方案设计方向不同（如新增 API vs 删除冗余步骤），无法仅凭成本量化 | 列出方向 A vs B + 长期影响，让用户选择方向 |

向用户呈现时使用选项式 + 推荐 + 最小化格式，不在不确定时做单方面决定。

### 5.2 执行流程

1. 按上述规则计算各方案总成本：
   - 总成本有明确最低值 → 推荐该方案，向用户呈现分析结论等待确认
   - 存在不确定场景 → 向用户呈现候选选项，让用户决策后再执行
2. 用户确认后，精确修改相关文档——每处修改与步骤 1 的诊断严格对应
3. 修改完成后汇总变更清单：

```
修订汇总：

| 文件 | 修改内容 |
|:---|:---|
| <file> | <具体变更> |

修改依据：解决审计问题 <问题描述>
选择方案：<方案编号>，理由：<1-2 句>
总成本：<异质修改处数> + <残余维护成本> = <总成本>（对比：<次优方案总成本>）
```

---

## 行为规则

- 步骤 1~4 **只读不写**——分析和决策阶段不修改任何文件
- 步骤 5 在用户确认后才修改文件——不擅自执行
- 每次只解决一个审计问题，不批量处理
- 如果步骤 3 判定所有方案都过度设计，输出"无需修改"并说明理由
- 如果问题涉及跨模块类型对齐，优先选择与已有先例（如 Tier 枚举）一致的模式
- 宪章原则五是硬性过滤条件，不是软性建议
- 所有输出使用中文
