## 步骤 1：加载上下文

1. 读取 `xspec/xf/constitution.md` 了解核心原则和技术方向
2. 读取 `xspec/xf/changes/change.yaml` 获取受影响模块列表和功能范围边界（scope）
3. 读取各模块的 `xspec/xf/changes/<module>/spec.md` 或 `spec.delta.md` 了解模块级需求规范
4. 对于变更模块：读取 `xspec/xf/modules/<name>/` 下已有文档了解现状
5. 读取 `xspec/xf/PRODUCT.md` 了解各模块的**职责边界、产品边界（做什么/不做什么）与模块依赖关系**——这是 /xf-split 声明的模块契约，本次概要设计不得超出

## 步骤 2：概要设计（逐模块）

对每个受影响模块，执行以下设计流程：

### 2.1 技术范围界定

向用户展示分析结果，获得确认：

```
📐 [module-name] 概要设计

技术范围：
  起点：[输入来源]
  终点：[输出目标]
  解决的问题：[一句话总结]

技术边界：
  上游：[依赖方]
  下游：[被依赖方]
  不涉及：[明确排除]

> 对齐校验：上述范围与边界须与 PRODUCT.md 中该模块声明的职责、依赖方向一致。
> 若发现本次设计需要超出模块声明职责、或引入 PRODUCT.md 未声明的依赖（含反向依赖），
> **不要擅自扩边界**，提示用户先回 /xf-split 修订模块结构再继续。

推荐：选项 A — 范围界定准确，继续设计

| 选项 | 说明 |
| :--- | :--- |
| A | 范围准确，进入架构方向探索 |
| B | 需要调整（请说明） |

```

### 2.2 架构方向探索（轻量头脑风暴，1 轮）

在确定架构方案之前，先快速探索可选的架构方向。**聚焦架构层面，不涉及实现细节**。

基于技术范围和宪章约束，分析可行的架构方向。如果宪章或需求特征已明确指向唯一合理方向（如宪章要求单体架构、或需求规模决定了技术路线），直接采用并说明理由，跳过本步骤。只有存在多个可行方向时，才列出 2-3 个选项（推荐 + 最小化 + 选项表）：

```
🧭 [module-name] 架构方向探索

推荐：选项 A — [1-2 句推荐理由，基于宪章约束和需求特征]

| 选项 | 方向 | 核心思路 | 风险 |
| :--- | :--- | :--- | :--- |
| A | [方向1] | [一句话] | [主要风险] |
| B | [方向2]（最小化） | [一句话，最简单直接的路径] | [主要风险] |
| C | [方向3，如有] | [一句话] | [主要风险] |

```

用户确认后，将选定方向和理由记录到 hld.md 的「架构方向探索」部分。

**注意**：这一步是快速定方向，不深入对比细节。如果某个方向涉及技术不确定性，步骤 3 会自主启动研究解决。

### 2.3 架构方案

基于用户选定的架构方向，展开概要级架构设计：

- 整体架构图（mermaid flowchart）
- 核心流程图（mermaid sequence diagram）
- 技术选型建议（框架、数据库、中间件等）

展示给用户确认（选项表 + 推荐 + 最小化）：

```
推荐：选项 A — 按上述方案推进

| 选项 | 说明 |
| :--- | :--- |
| A | 确认上述架构方案，进入下一步 |
| B | 需要调整（请简述调整方向） |
| C | 简化架构，采用最直接的实现路径（最小化） |

```

### 2.4 宪章合规检查

对照 `constitution.md` 检查：

- 技术选型是否符合宪章约束
- 架构方案是否满足非功能性要求
- 如有冲突，提出替代方案

## 步骤 3：技术研究（自主决定，xf-research subagent）

分析设计过程中是否存在**技术不确定项**（API 可用性、算法细节、性能特征、兼容性等）。

**硬规则**：
- **禁止**将技术不确定项标记为「待研究」「TODO」「留到实现阶段」。设计阶段发现的技术问题**必须在设计阶段解决**，这是「设计先行、研究先行」的核心原则。
- **自主决定**是否调用 `xf-research` subagent——**不要询问用户**「是否需要研究」。如果存在不确定项，直接启动研究。
- 若判断无技术不确定项，跳过本步骤即可。

**触发研究的信号**（满足任一即应启动）：
- 涉及团队未使用过的 API / 框架 / 技术模式
- 存在 2 个以上有竞争力的技术选型
- 需要 benchmark 或 PoC 验证
- 特定平台/版本的 API 可用性或行为不确定

**调用方式**：使用 `xf-research` subagent，传递以下上下文：
- **研究课题**：识别出的技术不确定项（含影响范围）
- **模块信息**：模块名称、类型
- **宪章约束**：`xspec/xf/constitution.md` 中的技术约束
- **已有决策**：步骤 2 中已确认的技术选型
- **输出路径**：`xspec/xf/changes/<module>/research.md`（索引）及 `research/` 子目录（深研究子文件）

subagent 完成后，读取 `research.md` 索引表中的结论摘要，**基于结论调整概要设计**（如结论影响架构方向，须更新 hld.md 相应部分）。

## 步骤 4：生成概要设计文档

design 阶段每个模块的产物为 `hld.md`（或 `hld.delta.md`）。按 `change_type` 区分输出：

**新增模块**（`change_type: added`）：
1. 读取该模块类型的 hld 模板：`.xflow/xf/templates/<resolved_type>/hld.md`。`resolved_type` 由 manifest 查询获得（自定义类型自动回退 `_default`）：
   ```bash
   node .xflow/scripts/xf-manifest.mjs --module-type <module_type> --phase design
   ```
   若 `.xflow/xf/templates/<resolved_type>/hld.md` 不存在，回退 `.xflow/xf/templates/_default/hld.md`。
2. 填充实际设计内容
3. 写入 `xspec/xf/changes/<module>/hld.md`（若 clarify/detail 阶段的 scaffold 已铺好 `hld.md` 骨架，直接在其上填充即可）

**变更模块**（`change_type: modified`）：
1. 读取 `xspec/xf/modules/<name>/hld.md` 和 `module.yaml` 了解现有概要设计及版本
2. 基于现有设计和本次变更需求，生成 `xspec/xf/changes/<module>/hld.delta.md`（格式见下方）

### hld.delta.md 格式

```markdown
# [模块名] 概要设计变更 — [变更ID]

> 基线：xspec/xf/modules/<name>/hld.md (v<version>)

## 变更摘要
[一句话描述架构变更核心内容]

## 架构变更
[用 mermaid 图展示变更部分]

## 技术选型变更
[原选型] → [新选型]，理由：[说明]

## 新增组件
[新增的架构组件及职责]
```

## 行为规则

- 需要用户做选择时，必须调用 question 工具以选项形式呈现（2-3 个选项 + 推荐 + 最小化），尽量不让用户手动输入
- 架构方向探索聚焦「架构层面」：单体/微服务、同步/异步、数据存储范式等，不涉及具体库和实现方案
- 概要设计聚焦「技术范围、架构方案、技术选型」，不涉及详细实现
- 尊重 /xf-split 在 PRODUCT.md 声明的模块契约：设计范围不得超出模块职责，不得引入未声明的依赖；需变更模块边界时先回 /xf-split 修订
- 所有架构和流程使用 mermaid 图表展示
- 技术选型必须对照宪章合规
- **设计阶段不允许留技术 TODO**：发现不确定项必须当场用 `xf-research` subagent 研究解决，不得标记「待确认」「留到实现」
- research 调用由 agent **自主决定**，不询问用户；subagent 结果按深浅分治写入 research.md 索引及 research/ 子文件
- 自定义 `module_type` 无专属模板时回退通用模板
- 所有输出使用中文

## 完成后验证

完成以上任务后，运行结构化验证：

```bash
node .xflow/scripts/xf-validate.mjs --node xf-design --flow xf
```

该脚本返回 JSON，包含**两类检查，都必须处理**：

1. **机械检查**（脚本自动判定，看 `pass` / `mechanical[]`）：
   - `pass: false`（exit≠0）→ 按 `mechanical[]` 中每条 `fail` 的 `detail` 修复（补齐缺失文件、清除占位符、补章节等），然后**重新运行脚本**，直到通过。

2. **语义检查**（脚本**不自动判定**，`semantic[]` 是交给你亲自执行的清单）。这一步最容易走过场，因此有**硬性取证要求：没有过程依据的 PASS 一律无效**。对 `semantic[]` 中**每一条**，按下述三步执行并留痕：

   a. **验证时重新读盘**：对该规则涉及的产物文件（及其依赖的上游制品）**当场重新 Read 一遍**，**不得**凭"刚才生成的内容"或对话记忆判断——文件可能在生成后被改动或删除，只有此刻磁盘上的内容算数。
   b. **摘录取证**：从刚读到的内容里**摘一小段原文**（加引号，标明「文件路径 # 章节/行」）作为依据；需要跨文件对照的规则，涉及的**每个文件都要摘**。
   c. **对照判定**：拿摘录去比对该条 `fail_condition`，得出 PASS/FAIL 并说明为什么。

   若某条 `fail_condition` 属于"某文件/产物必须存在"一类：一律以**当场读盘 / 列目录的实际输出**为准并把结果贴出来，禁止凭记忆或"刚生成过"下结论；判定涉及的清单（如受影响模块名）从其事实源（如 `change.yaml`）**现取**，不凭记忆。**具体查哪些文件、按什么标准，完全以该条 `fail_condition` 的描述为准**——这些由 Flow 配置（web 侧语义检查）定义；本 wrapper 通用于所有 Flow，不预设任何目录结构。

   逐条按此格式输出（**缺「依据」栏即视为 FAIL**）：
   ```
   [PASS/FAIL] <name>
     依据：读取 <文件路径>#<章节/行>，见「<原文摘录>」（存在性类：贴 ls/Read 的实际结果）
     结论：<对照 fail_condition，为什么满足 / 不满足>
   ```

   任一条 FAIL → **立即修复产物**，然后**重新读盘复核该条**（若牵动机械检查，一并重跑脚本），直到带依据判为 PASS。
   > 有些节点的产出路径无法预先声明（如拆分阶段模块名运行时才定），这类正确性**只能靠语义检查**保证，因此 `semantic[]` 不可跳过。

**仅当机械检查 `pass: true` 且 `semantic[]` 每条都带「依据 + 结论」判为 PASS 时，才可告知用户"节点已完成"。** 只写结论、给不出原文摘录的 PASS 无效，必须补取证或改判 FAIL。任一未过：把验证报告原文 + 你的逐条取证判定展示给用户，修复后重来，**不得跳过语义检查、也不得无依据直接报完成**。

随后对本节点制品再跑一次质量检查（**检测即止 · 不作为本节点完成门禁**；结果写入 `~/.xflow`，由 Web 端展示并作为人工审批依据）：

```bash
node .xflow/scripts/xf-quality.mjs --node xf-design --flow xf --l1-only
```

`rules[]` 结果逐条 `[PASS/FAIL] <rule> <name>` 如实列入完成报告（`l1_fail` 不得隐瞒）。**对 FAIL/阻断项，主 agent 必须当场修复产物并重跑复核，不得只报告不处理**；确实无法修复的，如实列明原因并提示用户。`need_judge` 语义项由主 agent **调用 subagent** 按输出中的 evidence 当场判定 `PASS/FAIL + 逐字依据`。
