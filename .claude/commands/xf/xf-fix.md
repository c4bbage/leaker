# /xf-fix：快速修复

## 目标

`/xf-fix` 用于处理不值得重新启动完整 Flow 的临时 Bug。它不创建新的 change，也不推进 phase，而是根据当前是否存在活跃 change，选择正确的位置保存修复事实。

| 当前状态 | 处理方式 | 原因 |
| :--- | :--- | :--- |
| 有活跃 change | 修复代码和测试，将修复过程记录写入 `changes/fix.md`，如当前 change 文档事实错误或缺失则立即同步 | 当前变更尚未归档，`modules/` 必须继续代表已确认的稳定事实 |
| 无活跃 change | 修复代码和测试，只有 `modules/` 稳定事实错误或缺失时才修改已有 modules 文档，不创建 `fix.md` | 当前没有待归档工作区，Agent 的长期上下文需要及时恢复正确 |

它要求**定位真正根因、把 Bug 对照到被违反的规范、并沉淀防复发的不变量**。`fix.md` 只是修复过程记录，不是需求来源，不写入 `source_doc`，不等待 brainstorm/clarify 消费。

`/xf-fix` 后的自然语言澄清和确认仍属于本次修复。用户执行其他 Slash Command 时，表示工作意图已经切换，本次 modules 写入权限随之关闭；如需继续修复，应重新执行 `/xf-fix`。

如果活跃 change 已处于 `xf-archive`，立即停止，不修改任何文件。归档阶段的 candidate、Diff 和写回计划可能已经形成，中途修复会使这些结果失效。

## 边界

**有活跃 change 时，绝不触碰 SSoT，也绝不伪造正常流程**——因为 SSoT 的写入权只属于归档节点：

- 不写 `xspec/<flow>/modules/`、`xspec/<flow>/archive/`、`.gates/`；
- 不改 phase，不执行或代替审批，不调用归档；
- 不调用任何 Flow 脚本（`xf-enter-node` / `xf-set-phase` / `xf-change-id` / `xf-fix-promote`），不创建或修改 `change.yaml`，不造 Change ID / Fix ID，不建 `.bugfix/`、`fix.json` 等平行工作区或独立 Bugfix 生命周期。

**无活跃 change 时**，允许直接修正 `xspec/<flow>/modules/` 中与 Bug 相关的现有文档，但：

- 只修正已有模块，不用于创建模块、删除模块或重新划分模块职责；这些结构性变化需要正常 Flow 重新确认。
- 不写 `xspec/<flow>/archive/`、`.gates/`；
- 不改 phase，不创建 `change.yaml`，不造 Change ID / Fix ID；
- 没有 Change ID 时，不虚构 `module.yaml` 的版本、`change_history` 或归档信息。

其余实操约束：

- 不提交或推送 Git，不安装依赖，不降低测试标准（不删必要测试、不放宽断言）。
- **若当前活跃 change 的 phase 已是 `xf-archive`（归档结算 SSoT 进行中），立即停止**：不建/改 `fix.md`、不动代码，提示用户先完成或退出归档——此时插入修复会破坏对账。

---

## 步骤一：读取当前状态

第一项状态检查必须通过 Bash 工具运行：

```bash
node .xflow/scripts/xf-current-change.mjs
```

必须解析脚本返回结果，确认：

- 是否存在活跃 change；
- change ID；
- 当前 phase；
- `yaml_path`；
- 受影响模块。

脚本不存在、执行失败或结果无法解析时，立即停止，禁止通过目录扫描代替该脚本推断状态。

脚本成功后，再确定当前 Flow：

1. 如果 `yaml_path` 非空，从：

   ```text
   xspec/<flow>/changes/change.yaml
   ```

   的路径中取得 `<flow>`，并确认：

   ```text
   .xflow/<flow>/Flow.yaml
   ```

   存在。

2. 如果没有活跃 change，检查实际安装的：

   ```text
   .xflow/<flow>/Flow.yaml
   ```

3. 如果只存在一个 Flow，以其目录名作为当前 Flow。

4. 如果存在多个 Flow，向用户展示真实 Flow 名称并要求选择；用户选择前不得创建或修改任何文件。

5. 如果无法确定 Flow，或 `.xflow/<flow>/` 与 `xspec/<flow>/` 不一致，立即停止，禁止猜测。

有活跃 change 时，修复记录路径为：

```text
xspec/<flow>/changes/fix.md
```

无活跃 change 时，不创建修复记录文件，修复事实直接写入对应 `modules/` 文档。

---

## 步骤二：读取修复上下文

### 有活跃 change

读取现有 `fix.md`（可能已累积多笔修复）。`fix.md` 是**本轮 `changes/` 的修复过程记录**——一个文件可以容纳多笔修复，最终整体随 `changes/` 一起归档。Fix 本次就完成代码、测试和必要的当前 change 文档同步，不等待未来 Brainstorm/Clarify 消费。多笔累积必须小心：

- 先完整读取现有内容。每笔修复是一个独立的 `## 修复项` 章节，**最新的放最上（newest-first）**，方便一眼看到近期改动。
- 处理**同一个 Bug**（继续/追加修复）：更新原修复项，不新建。
- 处理**新的、不相关的 Bug**：在文件顶部追加一个新修复项。
- **绝不覆盖、删除或清空任何已有修复项**，也不为不同 Bug 另建第二个 fix 文件——历史必须完整。
- 每笔修复都带「文档同步」字段，记录本次修复对当前 change 文档的同步结果。`fix.md` 不是需求来源，不得写入 `source_doc`，不作为未来需求流程的输入。

同时读取：

- `xspec/<flow>/changes/change.yaml`；
- 本轮已经存在、与 Bug 有关的变更文档；
- Bug 涉及模块在 `xspec/<flow>/modules/<module>/` 下的当前基线。

从 `change.yaml` 确认 `affected_modules`、`change_type` 和 `module_type`。如果 Bug 涉及的模块不在 `affected_modules` 中，向用户说明当前变更范围无法覆盖该修复并停止。

### 无活跃 change

不读取也不创建 `fix.md`。读取：

- `xspec/<flow>/PRODUCT.md`；
- Bug 涉及模块的 `module.yaml`；
- 该模块中与 Bug 有关的现有正式文档；
- Bug 相关的代码和测试。

模块名称、类型和职责必须来自现有材料。

---

## 步骤三：定位根因（先诊断，不急着改）

参考成熟调试实践，先找到**真正根因**再动手，避免只压掉表面症状：

1. 稳定复现 Bug——记录触发场景与条件，而不只是报错信息。
2. 沿调用链回溯到根因，而非第一个症状点；必要时与相邻的正常代码对比找差异。
3. 给出一个能解释全部现象的明确假设。

> **3 次失败护栏**：同一 Bug 连续 3 次尝试仍修不好，停止继续打补丁，转而质疑设计/架构，或建议走正常 Flow 重新澄清——不再堆叠临时修改。

---

## 步骤四：对照真相源，判定修复类型

读取相关模块的当前规范，把 Bug **映射到它违反了哪条需求 / 验收标准**，据此判定类型——这一步决定这笔债之后怎么还。

**读取范围：**

- 有活跃 change：读 `xspec/<flow>/changes/change.yaml` 及其 `affected_modules` 对应的变更文档，加上 `xspec/<flow>/modules/<module>/` 基线。Bug 涉及的模块若不在 `affected_modules` 内，**不得偷偷扩范围**——说明冲突并停止，等用户决定是否先调整变更范围。
- 无活跃 change：读 `xspec/<flow>/PRODUCT.md` 与 `xspec/<flow>/modules/<module>/`。模块名与 `module_type` 取自现有文件，不猜测。

**判定类型：**

- **实现缺陷**（代码 ≠ 规范）：规范是对的、代码错了。可就地修，并把"防复发"的边界补成**新 AC / 不变量**。
- **规范缺口 / 错误**（规范没覆盖，或规范本身写错）：根因在真相源。代码可以先修，但真正的解决必须改规范。

有活跃 change 时：
- **实现缺陷**（代码 ≠ 规范）：就地修代码和测试。文档同步：无需修改。
- **规范缺口 / 错误**（规范没覆盖，或规范本身写错）：修代码和测试的同时，立即同步对应的 `changes/` 文档（合入正确章节、清理冲突旧表述）。文档同步：已完成（列出文件）。本命令仍不改 `modules/`。无法完成文档同步时，状态写"部分完成"，记录"文档同步：未完成（列出原因）"，明确提示归档前必须人工处理。
- 不得把"新增 AC/不变量只记进 fix.md"当作正式规范同步；如果确实出现新的正式规则，属于规范缺口，必须同步正确的 changes 文档。

无活跃 change 时：
- 实现缺陷：修正代码和测试；现有模块规范仍然正确时，不为凑记录而修改 modules。
- 规范缺口或错误：用户确认后，将正确事实合入 Bug 涉及的已有 modules 文档，同时清理冲突旧表述；不得只在文末追加与正文冲突的补丁。
- 不建 `change.yaml`、不建模块变更目录、不造 spec/design/task 等标准制品。

---

## 步骤五：确认方案并写修复计划（先计划，后改码）

改任何业务代码前，先与用户确认：

- 需要用户明确确认：根因、最终方案、影响范围——尤其是 **Current（现状）/ Expected（期望）/ Unchanged（必须保持不变的行为）**。用户输入已清楚就不重复问；只在会改变修复结果的关键歧义处提问，且一次只问一个。
- 可以给推荐方案，但用户明确确认前不改业务代码。

### 有活跃 change

把计划写进 `fix.md` 对应修复项，状态先写 `处理中`。按下方模板创建或更新：

### fix.md 修复项模板

```markdown
# 临时修复记录

<!-- 最新修复项放最上；每个 Bug 一个 `## 修复项`；不删历史 -->

## 修复项：<单行标题>

- 状态：处理中 / 部分完成 / 已完成
- 文档同步：无需修改 / 已完成（列出文件） / 未完成（列出原因）
- 记录日期：<YYYY-MM-DD>
- 修复类型：实现缺陷（代码≠规范） / 规范缺口（真相源需变更）
- 关联变更：<change ID>
- 当前阶段：<phase；没有则写"无">
- 受影响模块：<真实模块名>
- 映射规范：<module>/spec.md#<被违反的需求或 AC；找不到→很可能是规范缺口>

### Current（现状 / 可复现）
<能复现的错误行为 + 触发场景>

### Expected（期望）
<修复后必须满足的行为>

### Unchanged（必须保持不变）
<明确不该被这次修复影响的行为，用于防回归>

### 根因
<回溯到的真正原因，不是症状>

### 最终方案（用户已确认）
<方案>

### 确立的不变量 / 边界
- INVARIANT: <此后永不能再坏的性质>
- EDGE CASE: <本次明确不覆盖的情况>

### 修改结果
- 代码：待实施
- 测试：待实施

### 验证结果
- 待实施

### 尚未验证
- <没有则写"无">

### 文档同步结果
<无需修改 / 已完成（列出同步的文件） / 未完成（列出原因，归档前必须人工处理）>
```

要求：只记最终采用的方案（不堆废弃方案）；内容与实际模块文档一致；不用模糊描述代替可验证结果；不写账号、密码、令牌、`.env` 等敏感信息。

### 无活跃 change

不创建 `fix.md`。方案确认后直接进入实施，修复事实将在步骤六中直接写入 `modules/`。

---

## 步骤六：最小修复 + 回归保护

计划确认后：

1. **先检查现有正式测试能否稳定复现本 Bug**：

   - 现有测试已覆盖目标行为，并且至少一个正确断言真实失败：直接复用现有测试并记录失败证据，不新增或修改重复测试；
   - 已有测试文件，但没有覆盖本次触发条件或边界：新增一个最小失败测试；
   - 测试声称覆盖该行为但仍然通过：先检查复现场景、测试有效性和根因，不得把"测试通过"冒充复现成功，也不得修改正确断言去迎合错误实现。

   修复代码后必须重新运行相关正式测试，确认原失败转为通过，并确保既有测试无回归。
2. **最小修复**：只改本次 Bug 真正涉及的代码，不顺手动无关文件。
3. **回归保护**：为步骤五里的 Unchanged 行为补/跑测试，确认没搞坏别的。
4. 运行范围最小但足以证明结果的相关测试。

5. 有活跃 change 且本次修复使 `changes/` 里现有规则失效或冲突：同步改正 `changes/` 对应文档（合入正确章节、清理冲突旧表述），但**不改 `modules/`**。
6. 无活跃 change 时，如果修复改变了模块当前应遵守的事实，同步修正 Bug 涉及的已有 modules 文档；将新规则合入正确章节并清理冲突旧表述，不创建新模块或扩大模块职责。

测试失败时：先分析原因，不删必要测试、不放宽断言、不绕过失败；解决不了就如实记录并停止，不报"已完成"。

---

## 步骤七：回填修复结果

代码与测试处理完，**重新读取实际文件和测试输出**，确认文档描述与实际代码行为一致，没有遗留占位符、待实施内容或相互冲突的规则。

### 有活跃 change

回填 `fix.md` 对应修复项：

```markdown
### 修改结果
- 代码：`<实际修改的文件>` — <说明>
- 测试：`<实际新增/修改的测试文件>` — <复现 / 回归覆盖>

### 验证结果
- `<实际执行的命令>`：通过 X / 失败 Y / 跳过 Z
```

并补全「确立的不变量 / 边界」和「文档同步结果」。

- 相关验证全部通过且文档同步已完成或无需修改 → 状态写 `已完成`；仍有失败、阻断或文档同步未完成 → 写 `部分完成` 并如实记录原因。
- **文档同步未完成时必须明确报告**，不得写已完成；提示用户归档前必须人工处理。

### 无活跃 change

不创建修复记录文件，验证结果直接向用户说明。

---

## 步骤八：完成报告

向用户报告：

```text
✅/⚠️ 临时修复处理完成

当前 Flow：<flow>
活跃 change：<存在/不存在>    关联变更：<change ID/无>    当前 phase：<phase/无>

本次处理的修复项：
- <标题>（<修复类型>）：<一句话结果>

Bug / 正确结果：
- <表现> → <预期>

根因：
- <根因>

修改文件：
- <代码文件> / <测试文件> / <必要时：当前 change 文档 或 modules 文档>

测试结果：通过 X / 失败 Y / 跳过 Z
尚未验证：<内容或"无">
```

### 存在活跃 change 时

说明：change ID 与 phase 未变、未审批未归档、`modules/` 与 `archive/` 未动；修复记录随当前 change 归档；文档同步未完成时必须明确报告，不得写已完成；用户继续当前正常 Flow。

### 不存在活跃 change 时

说明：当前没有 `change.yaml`、Change ID、phase 或本次 `fix.md` 记录；代码、测试和 Bug 涉及的已有 modules 文档已经按确认方案保持一致；`archive/` 与 `.gates/` 未修改。

---

## 行为规则

- 所有输出使用中文；
- 先定位根因、写好计划，再改代码；
- 有活跃 change 时，全项目只维护一个 `xspec/<flow>/changes/fix.md`，多笔修复累积其中、newest-first、不删历史；
- 无活跃 change 时，不创建 `fix.md`，直接修正 `modules/` 中的错误事实；
- 不建立平行 Bugfix 生命周期，不自动补造 change 或 phase，不绕过正常 Flow，不自动归档；
- 不提交或推送 Git，不读取或展示敏感配置；
- 自动测试通过不得表述为产品已经上线。
