## 步骤 1：加载上下文
 
1. 读取 `xspec/xf/constitution.md` 了解项目约束
2. 读取 `xspec/xf/PRODUCT.md` 了解产品定位和模块结构
3. 如 `xspec/xf/changes/brainstorm.md` 存在，读取获取发散结果
4. 对于变更模块：读取 `xspec/xf/modules/<name>/spec.md` 了解现有规范

## 步骤 1.5：制品要点摘要（强制，先于任何追问）

在第一次向用户提问之前，必须输出一段**简短摘要**（各 3-8 条要点即可，只摘与本次需求可能相关的部分）：

1. **来自 `constitution.md`**：核心原则、技术方向、不可违背约束（引用原文短语或短句，勿冗长照抄）。
2. **来自 `PRODUCT.md`**：产品定位、目标用户/角色、产品级边界（做什么/不做什么）、模块结构中与本次相关的模块。

**硬规则（必须遵守）**：

- **禁止**用开放式问题让用户重复描述已在上述制品中写清的内容（例如不要再泛泛问「目标用户是谁」「产品是干什么的」）。
- **允许**在以下情况追问：① 用户本次输入与制品**不一致**需对齐；② 需要确认制品中的结论**是否仍适用于本变更**；③ 需要**功能级/变更级**细化（例如：相对 PRODUCT 中的用户画像，本功能主要覆盖哪条路径或哪类角色）。
- 若某方向在制品中已有答案，应写为**陈述 + 请确认是否仍适用**，而不是假装不知道从头问。
 
### 步骤 1.6：关于 fix.md 的边界（强制）

`xspec/xf/changes/fix.md` 是 `/xf-fix` 留下的**临时修复过程记录**，不是原始需求，也不是正式需求材料。

- **不得**因为发现 `fix.md` 存在就自动读取、领取、纳入或展示其中内容；
- **不得**把 `fix.md` 写入 `change.yaml` 的任何字段（包括但不限于 `source_doc`）；
- **不得**因为 `fix.md` 存在就创建 change、扩大当前需求范围或增加受影响模块；
- 只有当用户在本次输入中**明确点名**某条修复记录（如"参考 fix.md 里第 X 条"）时，才可将该条内容作为**普通补充背景**读取；
- 即使用户主动引用了 fix.md 中的内容，正式需求来源仍然是**用户当前输入**，不是 `fix.md` 本身。

## 步骤 2：差量澄清（逐题交互，最少提问）

### 2.0 提问原则（强制）

**核心：能自己定的就别问。** 只有当某个缺口会改变「做什么/不做什么」、且你无法给出有理由的默认答案时，才停下来问用户。

- **能确定则不问**：只要你能给出一个合理判断并用一句话解释理由，就**直接采用**，在步骤 3 摘要里注明「已按 X 处理（理由）」，不占提问名额。
- **实质问题上限**：整场**最多 3 个**需要用户作答的实质问题（不含步骤 1.5 摘要、不含步骤 3 的最终确认）。宁少勿多——0 题也可接受。
- **一次只展示一题**：每则回复只允许有 1 个待答问题。
- **两种问法**（挑更省事的那种）：
  - **确认式（首选）**：你已有明确倾向时，直接给出结论 + 一句理由，让用户「确认 / 改一下」二选一即可，不要罗列并列选项让用户比较。例：「我打算把 X 限定在 A 场景（因为 PRODUCT 已定位 A 用户）。可以吗？」
  - **选项式**：仅当确实存在**多个对等分叉、无明显优劣**时才用。此时**精简展示**——一行一个选项（`A. …／B. …`），首选项标 `（推荐）`，理由合并成一句放在末尾，不画表格、不给每项写理由。
- **优先用平台选择工具**呈现，让用户点选而非手输。
- **题内纠偏**：用户答得含糊时可在同一题内追问 1 次，不计新题。
- **早停**：用户说「够了/没有/跳过/进总结」等，立即停止排队问题，进入步骤 3。
- **不外泄内部规则**：不要向用户复述「问题预算/筛选判据/步骤号」等本文档的元规则，也不列「接下来还会问…」的清单。用户只应看到干净的一句话问题。

### 2.1 问题筛选（不展示给用户，强制执行）

在发出**第一题**之前，先识别所有候选缺口，然后**严格过滤**：

**以下问题禁止询问用户（AI 自主决策并记录理由）**：
- **技术实现细节**：存储方案、错误处理策略、缓存策略、日志范围等 → 留给 `/xf-design` 和 `/xf-detail` 阶段
- **宪章已有答案**：宪章核心原则或技术方向已明确约束的 → 直接采用宪章结论
- **PRODUCT.md 已有答案**：产品边界、目标用户等已写清的 → 不重复问
- **有合理默认值**：行业惯例或常见做法可以覆盖的 → 采用默认值并记录

**仅保留以下类型的问题**：
- **功能范围歧义**：用户描述的需求存在多种理解，影响做什么/不做什么
- **业务优先级**：多个功能点之间的优先级不明确
- **模块影响确认**：本次变更涉及哪些模块（固定占最后 1 题，见 2.3）

过滤后，**差量补缺题最多 2 道** + **模块影响确认 1 道** = 合计不超过 3 道。若判断**无高影响缺口**，差量题可为 0 道，仅发模块确认 1 题。

### 2.2 逐题循环

每收到上一题的有效答案后，用**一两句话**工作记忆当前结论，再发下一题；直到：队列为空、或已达 3 题、或用户早停。

### 2.3 模块影响确认（必占 1 题，通常放最后）

基于 `PRODUCT.md` 的模块列表，先陈述你建议的划分，再**同一题内**用选择题收束：

> ⚠️ **added vs modified 客观判据（务必先按此分类，再展示给用户）**：
>
> - 仅当 `xspec/xf/modules/<name>/spec.md` **物理存在** 时，该模块才算 `modified`
> - 否则一律视为 `added`（即便 PRODUCT.md "模块列表"里已注册并标"规划中"，也是 added——
>   因为还没有 spec.md 基线可供 delta 引用）
>
> **禁止**仅凭 PRODUCT.md 中模块名是否出现来判断 added/modified——PRODUCT.md 的"规划中"
> 状态意味着该模块尚未物化（无 spec.md），首次为它撰写规范就是 added。

```
基于需求分析，我建议本次变更涉及：

新增模块（added，xspec/xf/modules/<name>/spec.md 不存在）：
  - <module-a> (web-backend)：[一句话描述]

变更模块（modified，xspec/xf/modules/<name>/spec.md 已存在）：
  - <module-b> (web-frontend)：[影响说明]

模块依赖影响（如有）：
  - <module-b> → <module-a>
```

**推荐：直接同意上述划分。** 若无异议即采纳；如需调整，用一句话说明改哪条（如需求涉及 `PRODUCT.md` 中不存在的模块，须先提醒执行 `/xf-split`）。

## 步骤 3.5：确认 Change ID（强制）

Change ID 末尾带一段 4 位 hash，是为了避免多人同日基于本 SDD 并行开发时 `CHG-YYYYMMDD-NNN` 撞号、合并时冲突；因此 ID 必须由脚本生成、不可手编。

`xf-enter-node.mjs` 可能已经创建 `xspec/xf/changes/change.yaml`。正式生成产物前，必须先确认 Change ID：

1. 检查 `xspec/xf/changes/change.yaml` 是否存在。
2. 如果文件已经存在：
   - 读取其中现有 `id`；
   - 后续补全 `change.yaml` 时必须原样保留该 `id`；
   - 禁止重新生成、修改或覆盖现有 ID；
   - 历史 `CHG-YYYYMMDD-NNN` 和新格式 ID 都保持原样，不要求转换。
3. 如果文件不存在，必须通过 Bash 工具运行：

   ```bash
   node .xflow/scripts/xf-change-id.mjs --flow xf
   ```

4. 脚本成功时，解析其 JSON 输出并确认：
   - `ok` 为 `true`；
   - `id` 存在；
   - 新生成的 ID 严格匹配 `CHG-YYYYMMDD-001-XXXX`；
   - 末尾 Hash 为 4 位大写十六进制字符。
5. 把脚本返回的 ID 原样用于本轮新建的 `change.yaml`。同一个 change 只能生成一次 ID。

禁止 Agent 手工拼接、推测或固定填写 Change ID。脚本不存在、执行失败、JSON 无法解析或新 ID 格式不合法时，立即停止，不得创建 `change.yaml`。

## 步骤 4：生成产物

用户确认后：

1. 使用步骤 3.5 确认的 Change ID，按 `.xflow/xf/templates/_shared/change.yaml` 模板生成或补全 `xspec/xf/changes/change.yaml`。如果该文件已由入口脚本创建，必须在保留现有 `id` 的基础上补全其他字段，禁止整体重写时改变 ID。（**绝对路径从仓库根起算，禁止省略 `xspec/xf/` 前缀，否则会在项目根目录误建 `changes/` 目录**），确保：
   - `status` 设为 `"in-progress"`
   - 填写 `scope.include` / `scope.exclude`（功能范围边界）
   - 填写所有 `affected_modules`（含 `change_type`、`module_type`、`summary`）
   - **`change_type` 严格按步骤 2.3 客观判据填写**（看 `xspec/xf/modules/<name>/spec.md` 是否物理存在），
     **不要**根据 PRODUCT.md 中的注册情况推断
2. 按 `change_type` 为每个受影响模块生成需求规范（路径同样从 `xspec/xf/` 起算）：
   - `change_type: added`（新增模块）→ 生成 `xspec/xf/changes/<name>/spec.md`（完整需求规范）
   - `change_type: modified`（变更模块）→ 先读取 `xspec/xf/modules/<name>/spec.md` 和 `module.yaml` 了解现状及版本，生成 `xspec/xf/changes/<name>/spec.delta.md`（增量需求变更，格式见下方）
3. **仅对 `change_type: added` 的模块**调用 scaffold 脚本按模块类型铺齐骨架文件（脚本以 `.xflow/xf/templates/CATALOG.yaml` 为准决定复制哪些文件，模板取自 `.xflow/xf/templates/<module_type>/`，自定义类型自动回退 `.xflow/xf/templates/_default/`，已存在文件不覆盖）：

   ```bash
   node .xflow/scripts/xf-scaffold.mjs --module <module-name> --type <module_type>
   ```

   > modified 模块**不要**调用 scaffold（脚本对 `--change-type modified` 会 no-op），delta 文件由本步第 2 项 AI 自己撰写即可。

### spec.delta.md 格式

```markdown
# [模块名] 需求变更 — [变更ID]

> 基线：xspec/xf/modules/<name>/spec.md (v<version>)

## 变更摘要
[一句话描述本次需求变更核心内容]

## 新增需求
- [新增的功能点]
- **新增对象**（包括旧 prose 首次纳管；严格按下方统一顺序完成 scope、identity 与验收证据判定后再一次性写入）：
  ```
  ### FR-XXX（新增）
  acs: AC-XX, AC-YY

  [完整 FR 描述]
  ```

## 修改需求
- [原需求引用] → [修改后的内容]
- **修改对象**（仅限本轮写入前已拥有正式 FR identity 的对象；复用真实原 ID 并按下方规则整对象替换）：
  ```
  ### FR-XXX（修改）
  acs: AC-XX, AC-YY

  [完整 FR 描述]
  ```

## 新增验收标准
- [新增的 AC]
- 新增 AC 使用正式编号：`AC-XX`

## 修改验收标准
- **仅作回归说明**（旧 AC 仍适用、保持有效或不受影响）：写成 `- 原验收标准（引用：AC-XX）仍适用：[说明]` 这类先以叙述文字起行的格式，不生成正式 AC 对象；避免人读摘要被 parser 误识别为对象定义，污染 provenance / Effective View。
- **真正修改 AC 业务语义**：保留该 AC 的真实 ID，按对应 spec 模板完整写入正式 AC 对象；此时才由 Effective View 整对象 overwrite。

## 删除对象
- **删除 Node 使用机器字段**：
  ```
  removed: FR-XXX, AC-XX
  ```
  具体边界集中见下方 Relationship 需求协议。
```

## Relationship 需求协议

生成任何 `spec.md` / `spec.delta.md` Relationship 对象时，必须依次完成以下决策；前一步未完成，不得进入后一步：

1. **写入前冻结 identity snapshot**：在生成或修改任何 FR 正式对象头之前，只以本轮写入开始前的 Modules baseline 与已经存在的 Active Change 判断该业务对象是否已有正式 FR identity。本轮后来写入的草稿、临时或正式 FR 不能反向成为“已有 identity”的证据；这是为了避免 provisional / 猜号先污染 Active Change，再影响真实编号。
2. **先锁定最小 FR scope**：从用户本轮真正触达的最小业务能力确定 FR 自身边界，这一步必须早于 AC 选择。业务上属于“修改旧需求”不等于 Relationship 对象已经存在；不得为了复用更多 legacy AC，也不得因同章节、同主题或回归说明而扩大 FR scope。
3. **再决定 reuse / 发号**：snapshot 中已有正式 FR identity 时复用真实原 ID，不调用发号脚本；没有时，必须在写入任何正式或临时 `### FR-*` 对象头之前调用 `node .xflow/scripts/xf-relations.mjs --action next-id --module <name> --type fr`，并且只有收到返回的 `next_id` 后才能物化对象头。禁止 provisional ID、猜号、先写后查。当前 Change 中已经物化的新 FR 会为后续另一个新增对象占号，但不能据此给同一对象再次发号。
4. **先闭环 Existing AC 命运，再构造完整 `acs:`**：`acs:` 与 Effective View 表示当前事实，不是旧事实和新事实的叠加；若不先处理旧 AC，就可能让已失效事实与替代事实同时留在 Graph。对本轮直接触达的每个 existing AC，在新增 AC 前先判断：
   - **KEEP**：业务事实完整仍成立，保留原 identity，无需重写。
   - **MODIFY**：仍是同一个验收事实，但条件、行为或结果改变，复用真实原 ID 并按 spec 模板正式整对象 overwrite，而不是另建替代 identity。
   - **DELETE**：该验收事实或能力本身不再存在，写入 `removed:`，并从所有当前 `acs:` 移除。
   - 与任何 existing AC 都不是同一验收事实的，才是 **ADD**，使用新 identity。
   完成命运判定后，基于 KEEP + MODIFY + ADD 重算完整 `acs:`。该字段是“直接验证已锁定 FR scope 的完整当前有效验收证据集合”，不是本轮新增或改写的 AC 集合。必须回读 Modules baseline 与 Active Change 的真实业务语义，纳入本轮触达区域中直接验证该 FR 的 existing legacy AC，即使本轮无需改写，并保持其真实 identity；未触达的 legacy 对象不批量迁移。sibling 保持不变、回归保护、scope exclusion、“不受影响”以及仅同主题、同章节或编号相邻的 AC，不因被提及就自动成为该 FR 的验收证据。这样既不漏掉本轮触达且仍有效的旧验收，也不把只验证 sibling 业务的 AC 污染进 Graph。
5. **最后一次性物化对象**：全新需求或旧 prose 首次纳管都只建立一个“新增 Relationship identity”。即使本轮业务上修改了旧需求，也只在 `## 新增需求` 中正式定义一次；业务修改摘要可继续写在 `## 修改需求`，但不得再生成同 Key 的“修改对象”。只有本轮写入前已有正式 FR identity 的普通修改，才以真实同 Key 整对象替换，写入完整 FR 定义并保留仍有效的完整验收证据。一个 stable key 在同一 delta 中只能有一个正式定义，后续内容变化合并进该定义。

**Existing / Removal / ID 保持规则：**

- 已有 FR 的整对象替换不能只写自然语言 patch，也不能因遗漏静默丢边；若本轮明确只解除某条 FR→AC 关联，才从完整证据集合中移除该引用，这不等同于删除 AC Node。
- 只有删除 FR / AC Node 本身时才使用 `removed: FR-XXX, AC-XX`；unlink 不使用该字段。对象删除不得只靠自然语言表达，列表中禁止 `@module` 跨模块引用，被删除对象不得在同一 delta 中再次定义。
- FR 编号使用正式三位数（如 `FR-001`）；新建 AC 使用现有 canonical 1–3 位数字 ID 规则（如 `AC-01`）。修改或引用已有 AC 时保留 Modules baseline / Active Change 中的真实 identity；`AC-03a`、`AC-2024-001`、`AC-RBAC-01a`、`AC-LOGIN-V2-03` 等 legacy ID 不为 canonical 化而重编号。FR 的“历史 removed identity 也永不复用”保证不扩大到 AC。delta 是变化载体，不是新的命名空间，禁止 `FR-D01`、`AC-D01`、`DAC-01`、`DS-D01`、`T-D01` 等 delta 专用 ID。
- 真正 ADD 的 AC 需要新的 stable identity：`xf-relations next-id` 只负责 FR / DS，不用于 AC；新增 AC 按上述 canonical 规则，在本模块 Modules baseline 与 Active Change 的当前 identity snapshot 中选择未占用编号。本轮已通过 `removed:` 删除的 existing AC 仍占有其 stable key，不能在同一 Change 中立即把该 ID 赋给另一个新验收事实；这是为了让删除旧对象与新增新对象保持可区分。
- 人读摘要/修改说明中引用 FR / AC / DS / Task 时，不得让行首形成合法 Relationship 对象定义（如 `- AC-03 → 删除`、`- FR-001 → 修改` 等）；对象删除事实必须由上述机器字段唯一表达。
- 生成的 spec 必须遵循对应 module type 的 spec 模板。
- `acs:` 必须紧跟 FR 对象头并位于正文前；禁止在文末另建 FR/Relationship 索引。
- 上文 fenced block 只用于展示格式；实际 `spec.md` / `spec.delta.md` 中的正式 FR/AC 对象必须直接写在 Markdown 正文，禁止用 fenced code block 包裹，否则 parser 会按示例忽略。
## 步骤 4.5：Spec 内容质量检查（强制，在自检之前）

写完 spec.md / spec.delta.md 后，立即逐项检查：

1. **无技术实现泄漏**：功能描述中不出现框架名、库名、API 路径、表名
2. **验收标准完整**：每条 AC 都有完整的 Given/When/Then 三要素
3. **验收标准可衡量**：不含模糊词（等、若干、适当、合理、正常、部分）
4. **成功指标技术无关**：不提及具体技术组件（数据库、缓存、CDN 等）
5. **用户故事有优先级**：每个 US 都标注了 P0/P1/P2
6. **边界场景不为空**：每个功能至少列出 2 个异常/边界情况
7. **[待确认] 标记上限**：整个 spec 中 [待确认] 不超过 3 处
8. **Existing AC 命运闭环**：语义修改已用原 ID 正式 overwrite，删除对象已从 `acs:` 移除，且没有失效旧事实与替代新事实并存

发现问题则**立即修复并重新检查该项**（不等到步骤 5），最多 2 轮。

## 完成后验证

完成以上任务后，运行结构化验证：

```bash
node .xflow/scripts/xf-validate.mjs --node xf-clarify --flow xf
```

该脚本返回 JSON，包含**两类检查，都必须处理**：

1. **机械检查**（脚本自动判定，看 `pass` / `mechanical[]`）：
   - `pass: false`（exit≠0）→ 按 `mechanical[]` 中每条 `fail` 的 `detail` 修复（补齐缺失文件、清除占位符、补章节等），然后**重新运行脚本**，直到通过。

2. **语义检查**（脚本**不自动判定**，`semantic[]` 是交给你亲自执行的清单）。这一步最容易走过场，因此有**硬性取证要求：没有过程依据的 PASS 一律无效**。对 `semantic[]` 中**每一条**，按下述三步执行并留痕：

   a. **验证时重新读盘**：对该规则涉及的产物文件（及其依赖的上游制品）**当场重新 Read 一遍**，**不得**凭"刚才生成的内容"或对话记忆判断——文件可能在生成后被改动或删除，只有此刻磁盘上的内容算数。
   b. **摘录取证**：从刚读到的内容里**摘一小段原文**（加引号，标明「文件路径 # 章节/行」）作为依据；需要跨文件对照的规则，涉及的**每个文件都要摘**。
   c. **对照判定**：拿摘录去比对该条 `fail_condition`，得出 PASS/FAIL 并说明为什么。

   若某条 `fail_condition` 属于"某文件/产物必须存在"一类：一律以**当场读盘 / 列目录的实际输出**为准并把结果贴出来，禁止凭记忆或"刚生成过"下结论；判定涉及的清单（如受影响模块名）从其事实源（如 `change.yaml`）**现取**，不凭记忆。**具体查哪些文件、按什么标准，完全以该条 `fail_condition` 的描述为准**——这些由 Flow 配置（web 侧语义检查）定义；本 wrapper 通用于所有 Flow，不预设任何目录结构。

   逐条按此格式输出（**缺「依据」栏即视为 FAIL**）：
   ```
   [PASS/FAIL] <name>
     依据：读取 <文件路径>#<章节/行>，见「<原文摘录>」（存在性类：贴 ls/Read 的实际结果）
     结论：<对照 fail_condition，为什么满足 / 不满足>
   ```

   任一条 FAIL → **立即修复产物**，然后**重新读盘复核该条**（若牵动机械检查，一并重跑脚本），直到带依据判为 PASS。
   > 有些节点的产出路径无法预先声明（如拆分阶段模块名运行时才定），这类正确性**只能靠语义检查**保证，因此 `semantic[]` 不可跳过。

**仅当机械检查 `pass: true` 且 `semantic[]` 每条都带「依据 + 结论」判为 PASS 时，才可告知用户"节点已完成"。** 只写结论、给不出原文摘录的 PASS 无效，必须补取证或改判 FAIL。任一未过：把验证报告原文 + 你的逐条取证判定展示给用户，修复后重来，**不得跳过语义检查、也不得无依据直接报完成**。

随后对本节点制品再跑一次质量检查（**检测即止 · 不作为本节点完成门禁**；结果写入 `~/.xflow`，由 Web 端展示并作为人工审批依据）：

```bash
node .xflow/scripts/xf-quality.mjs --node xf-clarify --flow xf --l1-only
```

`rules[]` 结果逐条 `[PASS/FAIL] <rule> <name>` 如实列入完成报告（`l1_fail` 不得隐瞒）。**对 FAIL/阻断项，主 agent 必须当场修复产物并重跑复核，不得只报告不处理**；确实无法修复的，如实列明原因并提示用户。`need_judge` 语义项由主 agent **调用 subagent** 按输出中的 evidence 当场判定 `PASS/FAIL + 逐字依据`。
