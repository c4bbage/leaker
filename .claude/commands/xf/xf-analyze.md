请直接执行下述审计流程。审计对象是 `$ARGUMENTS` 指定的现有项目内容；本命令文件本身不是待开发或待测试的对象。

## 目标

`/xf-analyze` 是正常 Flow 之外的独立审计命令，不创建 change、不推进 phase，也不执行审批或归档。

根据当前是否存在活跃 change，行为分两种模式：

- **有活跃 change**：可在除 `xf-archive` 外的任意阶段立即执行；修复范围**随 phase 收紧**：
  - phase 早于 `xf-implement`（设计阶段：clarify/design/detail/task 等）→ 用户确认后**只允许修正 `xspec/xf/changes/` 下当前变更文档，禁止改业务代码和测试**（代码实现是 `/xf-implement` 的职责，不能越阶段提前实现）；
  - phase 为 `xf-implement` → 用户确认后允许修正本次审计涉及的业务代码、测试和 `xspec/xf/changes/` 下当前变更文档；
  - 两种情况都禁止修改 `xspec/xf/modules/`、`archive/` 和 `.gates/`。
- **无活跃 change**：不创建 `change.yaml`、Change ID 或 phase；用户确认后允许修正代码、测试和审计涉及的已有 `modules` 文档。

审计结果直接在会话中输出；用户确认修复后，修改直接落到实际代码、测试或文档中（改代码仅限上述允许的阶段），不额外创建独立审计记录文件。

`/xf-analyze` 后的自然语言澄清和确认仍属于本次审计；用户执行其他 Slash Command 后，本次 Analyze 工作结束。

## 边界

本命令不改变正常 Flow 生命周期：

- 不改 phase，不执行或代替审批，不调用归档；
- 不调用 `xf-enter-node`、`xf-set-phase`、`xf-validate` 或任何 Flow 推进脚本；
- 不创建或修改 `change.yaml`，不创建 Change ID 或平行审计生命周期；
- 不写入 `xspec/xf/archive/` 或 `.gates/`。

有活跃 change 时，不修改 `xspec/xf/modules/`。

无活跃 change 时，只允许修正审计涉及的已有模块及其当前事实；不得创建新模块、删除模块、扩大模块职责或伪造 `module.yaml` 的版本、`change_history` 和归档记录。

若当前活跃 change 的 phase 是 `xf-archive`，立即停止，不修改任何文件。归档期间插入审计会破坏已经确认的归档内容。

对当前变更的设计制品进行跨文档一致性审计，发现并解决问题。

本命令分两个阶段：
1. **首轮审计（只读）**：执行步骤 1–9A 检查，输出问题报告，**不修改任何文件**。
2. **自动修复 loop（需用户确认后才进入）**：按「修复 → 复检」迭代，直到达到终止标准或触及轮数上限。

**参数解析**：从 `$ARGUMENTS` 中解析两类信息（都可选，去除首尾空白）：

**(a) 审计范围（模块关键词）**
- **无模块关键词**：审计当前变更下的**全部模块**
- **指定模块名或前缀**（如 `user-auth`、`001`）：仅审计匹配的模块，跨模块检查（步骤 4/5/6）仅涉及该模块与其关联模块

模块匹配规则（有活跃 change 时查 `xspec/xf/changes/`；无活跃 change 时查 `xspec/xf/modules/`）：
1. 精确匹配：对应目录下 `<keyword>/` 存在 → 直接使用
2. 前缀匹配：查找对应目录下以 `<keyword>` 开头的目录（如输入 `001` 匹配 `001-login`）
3. 匹配到唯一目录 → 直接使用；匹配到多个 → 列出让用户选择；无匹配 → 列出所有可用模块后终止

**(b) 终止标准（自然语言，决定 loop 修到什么程度算「没问题」）**
- 用户可自定义，例如「修到无高危」「零问题」「高中危都清掉」等
- **未指定时默认：修复到无「高危」且无「中危」问题**（低危仅保留在报告中，不强制修）
- 把用户的自然语言标准归一化为一个「严重度阈值」：`高` / `高+中`（默认）/ `全部`，供步骤 11/12 判定使用

## 步骤 1：确定审计范围并加载制品

### 1.1 确定目标模块

- **有活跃 change + 全量模式**（无参数）：从 `xspec/xf/changes/change.yaml` 的 `affected_modules` 获取所有模块列表
- **有活跃 change + 单模块模式**（有参数）：仅使用指定的模块名
- **无活跃 change + 全量模式**：从 `xspec/xf/modules/` 现有模块目录获取审计范围
- **无活跃 change + 单模块模式**：仅使用指定的模块名，该模块须在 `xspec/xf/modules/` 下已存在

### 1.2 加载公共制品

- `xspec/xf/constitution.md`（项目宪章）
- 有活跃 change 时额外加载：
  - `xspec/xf/changes/change.yaml`（变更元数据 + scope 功能范围边界）
  - `xspec/xf/changes/brainstorm.md`（头脑风暴记录，如存在）
  - `xspec/xf/changes/integration.md`（跨模块协调视图，如存在）
- 无活跃 change 时：跳过 `changes/` 下文件，改读 `xspec/xf/PRODUCT.md`（如存在）

### 1.3 加载模块制品

对每个目标模块，按其 `module_type` 对应的制品清单读取对应文件（**不要硬编码文件名**——不同 `module_type` 的制品集不同）。有活跃 change 时读取 `xspec/xf/changes/<name>/`；无活跃 change 时读取 `xspec/xf/modules/<name>/`。典型覆盖项：

- `spec.md` / `spec.delta.md`（clarify 阶段，所有类型 required）
- `hld.md` / `hld.delta.md`（design 阶段，所有类型 required）
- `design.md` / `design.delta.md`（detail 阶段）
- `data-model.md` / `data-model.delta.md`（detail 阶段）
- `contracts.md` / `contracts.delta.md`（detail 阶段，仅该类型包含此项；`systems` / `ai-agent` / 通用类型不含）
- `evaluation.md` / `evaluation.delta.md`（detail 阶段，仅 `ai-agent` 专属）
- `task.md`（task 阶段，所有类型 required）

额外可选读取（与 module_type 无关）：`research.md` + `research/` 子文件。

> 单模块模式下，如果步骤 4/5/6 需要跨模块对比（如前后端 contracts 对齐），额外加载关联模块的关键文件。

## 步骤 2：需求覆盖检查

**目标**：确保功能点都在模块级 spec 中有对应内容。

1. 有活跃 change：从 `xspec/xf/changes/change.yaml` 的 `scope.include` 提取功能点列表；无活跃 change：从 `xspec/xf/PRODUCT.md` 或模块 spec 中提取功能点列表
2. 对每个功能点，检查是否在某个模块的 `spec.md`（或 `spec.delta.md`）中有对应章节
3. 输出覆盖率：`N/M (XX%)`

**问题标记**：
- 功能点未在任何模块 spec 中出现 → **高**
- 功能点仅简要提及但无详细描述 → **中**

## 步骤 3：任务覆盖检查

**目标**：确保 spec 中的验收标准都有对应的实现任务。

1. 从所有模块的 `spec.md`（或 `spec.delta.md`）中提取验收标准（AC-XX 编号）
2. 对每个验收标准，检查各模块 `task.md` 中是否有对应任务
3. 输出覆盖率：`N/M (XX%)`

**问题标记**：
- P0 验收标准无对应任务 → **高**
- P1 验收标准无对应任务 → **中**
- P2 验收标准无对应任务 → **低**

## 步骤 4：集成任务检查

**目标**：如存在 `integration.md`，检查跨模块集成任务的完整性。

执行需求—设计—任务关系核对、依赖追踪或影响分析时，加载并遵循 skill `xflow-relationship-graph`。
对于跨模块依赖（`depends: TNNN@module`）、FR→DS→Task 追溯、DS→FR 反向核对，必须使用 CLI `query` 获取真实 Graph 关系事实，不得仅靠全文搜索或记忆声称关系成立。CLI 返回 `source` 后必须回读对应 Markdown 原文再做业务解释。

1. 集成任务中的 `depends: TNNN@module` 引用是否指向存在的模块任务
2. 涉及前后端的变更是否有联调集成任务
3. 质量门禁清单是否完整

**问题标记**：
- 跨模块依赖指向不存在的任务 → **高**
- 前后端变更缺少联调任务 → **中**
- 质量门禁缺失关键检查项 → **低**

如 `integration.md` 不存在（单模块变更），跳过此检查。

### 步骤 4.5：Relationship 结构化关系核对

**适用条件**：当前审计涉及已有模块的 FR / DS / Task 事实时强制执行。全新模块且无已有 Relationship baseline → 跳过，注明「不适用」。

适用时：

1. 从目标模块的 spec.md / design.md / task.md 内联对象提取实际 FR / DS / Task key。

2. 对焦点对象逐一执行真实 CLI `query`：
   ```bash
   node .xflow/scripts/xf-relations.mjs --action query --key <module/object-id>
   ```
   确认：FR→AC 关系完整、DS→FR 来源正确、Task→DS 追溯可验证、`depends` 链完整无悬空。

3. CLI 返回 `source` 后必须 Read 对应 Markdown 原文再判定，不得仅凭 CLI JSON 判 PASS/FAIL。

4. **impact（条件执行）**：仅当本次变更涉及已有 FR / DS / Task 的修改，或用户明确要求评估影响范围时执行：
   ```bash
   node .xflow/scripts/xf-relations.mjs --action impact --key <module/object-id> --depth 2
   ```
   选择当前 Change 真正的焦点对象，不要求对所有对象无脑 impact。多跳结果结合 `source` 精读后解释，不得仅凭返回节点自行判严重度。

   **删除对象特别规则**：Effective View 中已 `removed:` 的对象不再存在于最终 Graph，不得伪造对已删除 key 的 impact。删除场景通过 baseline/delta 文档事实 + validate 的 dangling 结果 + 对仍存在对象的 query/impact 判断删除是否留下错误关系。

**问题标记**：
- CLI query 发现 FR→AC / DS→FR / Task→DS 关系断裂 → **高**
- depends 链存在悬空引用（DANGLING_REFERENCE）→ **高**
- impact 发现多跳变更影响未在 spec/design 中体现 → **中**
- validate 报告 Graph 错误 → 按具体错误内容判定严重度

## 步骤 5：前后端 Contracts 对齐

**目标**：如果变更同时涉及前端和后端模块，确保接口定义一致。

**前置判断**：分别检查前端和后端模块的类型是否包含 `contracts.md`。**只要任一端不含 `contracts.md`，跳过此检查**（例如 `systems` 后端）。

1. 从后端模块 `contracts.md` 提取接口列表（方法、路径、参数、响应、错误码）
2. 从前端模块 `contracts.md` 提取调用列表
3. 逐接口对比路径、参数、响应、错误码

**问题标记**：
- 前端调用的接口后端未定义 → **高**
- 参数或响应字段不匹配 → **高**
- 后端有接口但前端未调用 → **中**
- 错误码处理不一致 → **中**

如变更仅涉及单端，或任一端不含 `contracts.md`，跳过此检查。

## 步骤 6：数据模型对齐

**目标**：确保前后端的数据结构定义匹配。

**前置判断**：检查前后端模块是否均含 `data-model.md`（当前所有注册类型均含，但自定义类型回退通用模板时此文件为 optional，需确认实际存在）。

1. 从后端 `data-model.md` 提取表结构和字段
2. 从前端 `data-model.md` 提取 TypeScript 接口/类型
3. 对比字段、类型兼容性、命名风格

**问题标记**：
- 后端响应字段在前端类型中缺失 → **高**
- 类型不兼容 → **中**
- 命名风格不一致且未说明转换规则 → **低**

## 步骤 7：宪章合规检查

**目标**：确保所有设计制品符合 `constitution.md` 的要求。

逐板块检查：
1. **核心原则**：设计中是否有违背
2. **技术约束**：design.md 中的技术选型是否在宪章允许范围内
3. **质量标准**：tasks 中是否有满足宪章要求的测试/性能任务
4. **安全与合规**：contracts 中的认证方式是否符合

**问题标记**：
- 违反核心原则/技术约束 → **高**
- 质量标准/安全要求未满足 → **中**

## 步骤 8：术语一致性检查

**目标**：发现跨文档的术语不一致。

检查同一概念在不同文档中是否使用不同称呼（如"用户" vs "账户"）。

**问题标记**：
- 同一概念不同业务术语 → **中**
- 仅命名风格差异（snake_case vs camelCase）→ **低**

## 步骤 9：歧义检测

**目标**：发现需求描述中的模糊表述。

扫描所有 `spec.md` / `spec.delta.md` 和 `hld.md` / `hld.delta.md`，检测模糊词汇：
"等"、"若干"、"适当"、"合理"、"如有必要"、"尽可能"，以及无具体数值的性能描述。

**问题标记**：
- 验收标准中的模糊表述 → **中**
- 功能描述中的模糊表述 → **低**

## 步骤 9A：规范—代码—测试三方一致性核对（只读，强制，独立审计）

**目标**：对每个目标模块，主动核对"规范期望—代码实际行为—测试断言"三方一致性。本步骤是**独立审计**，不依赖步骤 2–9 是否已发现问题——即使步骤 2–9 的文档审计全部通过，仍必须完成本步骤。

**范围约束**：不得扩大为全项目无边界扫描。只读取目标模块文档中声明的路径、接口、符号和 AC 所指向的代码与测试文件。

### ⚠️ phase 门控与实施状态判定（强制）

本步骤是否执行、以及能否改代码，取决于当前所处阶段。**判断依据是步骤 0 读到的 phase，不是「代码是否存在」**：

- **有活跃 change 且 phase 早于 `xf-implement`**（即 `xf-clarify` / `xf-design` / `xf-detail` / `xf-task` 等设计阶段）：**不针对本轮新需求检查或修改实现**。此阶段按 Flow 设计根本不应该有本轮的实现代码，代码实现属于后续 `/xf-implement` 的职责，不能越阶段提前实现。若发现设计阶段目录里已有不该存在的实现代码，只在报告里**提示异常**，不在本命令里补写或"对齐"代码。**本轮新需求尚未实施，不得判为实现缺陷或测试覆盖缺口**，单独列为「尚未实施 / N/A」。
- **有活跃 change 且 phase 为 `xf-implement`**：正常执行本步骤。只对已完成任务、已经修改的代码或明确声称完成的行为要求实现和测试存在；待执行任务不计为缺陷。
- **无活跃 change**（对已归档的既有模块审计）：正常执行本步骤，`modules/` 代表当前稳定事实，对应代码和测试原则上应已存在，可执行完整三方核对。
- **phase 为 `xf-archive`**：立即停止（步骤 0 已拦截，此处重申）。

**覆盖率分母规则**：分母只统计当前阶段应当已经实现的行为；尚未实施项单独列为 N/A，不得拉低覆盖率。

### 执行步骤

对每个目标模块执行：

1. **提取可验证行为清单**：从模块 `spec.md` / `spec.delta.md`、`contracts.md`、`data-model.md`、`task.md` 等制品中提取可验证行为、接口签名、字段定义和 AC 编号，形成清单。对每项标注"当前阶段是否应当已实现"（是 / 尚未实施）。

   **原子行为核对规则（强制）**：每项可验证行为必须按以下维度逐项拆分，不得合并或省略：
   - **输入**：参数类型、约束、合法/非法边界；
   - **输出**：返回值类型、语义（如"和""差""拼接"）、格式；
   - **异常**：触发条件、错误类型、错误信息内容；
   - **边界**：空值、极值、类型转换、幂等性；
   - **副作用**：状态变更、I/O、日志、事件。

   每项拆分结果必须记录：**文件路径 + 章节编号 + 规范原句**（逐字引用，不得改写）。禁止用章节标题、函数名或测试名代替具体语义比较——例如不得写"4.1 加法已覆盖"，必须写"spec.md §4.1：'输出：两个输入的数学和'"并与代码 `return first + second` 逐项比对。

2. **主动定位代码实现**：对"应当已实现"的每一项，根据规范声明的文件路径、函数名、接口路径，读取对应的业务代码实现，确认实际行为。
3. **主动定位正式测试**：对"应当已实现"的每一项，查找覆盖该行为的正式测试文件（`__tests__/`、`*.test.*`、`*.spec.*`），确认测试是否存在、断言是否覆盖规范行为。**首轮只读阶段不得运行测试**——只读取测试代码、判断覆盖关系；如用户已提供测试结果可引用，但不得主动执行测试命令。
4. **三方比较**：比较"规范期望—代码实际行为—测试断言"，对每项做出事实判定（六选一）：
   - **纯文档缺陷**：代码和测试正确，规范描述与实现不符 → 建议修改文档；
   - **实现缺陷**：应当已实现但代码缺失或代码行为与规范不符 → 建议修改代码；
   - **测试覆盖缺口**：代码存在且正确，但测试缺失或断言未覆盖规范行为 → 建议补充测试；
   - **代码与文档同时错误**：规范和实现均有偏差，需同步修改 → 明确列出文档、代码、测试各自的修改范围；
   - **无法确定事实**：证据不足或存在合理歧义 → 标记为「需人工决策」，**禁止自动修复**。
   - **尚未实施 / N/A**：当前阶段尚未要求实现的行为，不计入缺陷。

   **核心输出冲突硬规则（强制）**：核心输出、计算结果和错误条件只要与代码实际行为冲突，就**必须报告**；不能因为代码和测试彼此一致而忽略规范冲突。具体地：
   - 核心输出语义错误（如规范写"和"但代码执行"差"）**默认高危**，无论测试是否与代码一致；
   - 代码和测试均正确、而规范描述与实现不符时，判为**纯文档缺陷**（严重度按影响范围定），不得因"代码测试一致"而跳过报告。

5. **找不到实现或测试时**：不得默认修改文档来"对齐"缺失的实现。应按上述分类判定：应当已实现但代码缺失 → 实现缺陷；代码存在但测试缺失 → 测试覆盖缺口；无法确认是否应当存在 → 需人工决策。

### 有边界的定位回退

规范未直接写文件路径时，允许按以下线索做**有限搜索**：

- 模块名；
- 接口路径（如 `/api/users`）；
- 函数、类或组件名；
- task / design 中引用的符号。

只输出少量候选（≤5）并核实；候选过多或无法唯一定位时标记「需人工决策」，不得全项目无边界扫描。

### 输出（写入步骤 10 报告）

- 规范 → 实现覆盖率：`N/M (XX%)`（分母仅含当前阶段应当已实现的行为）
- 规范 → 测试覆盖率：`N/M (XX%)`（同上）
- 尚未实施 / N/A：K 项（单独列出，不计入覆盖率）
- 实现缺陷清单
- 测试覆盖缺口清单
- 纯文档缺陷清单
- 代码与文档同时错误清单
- 需人工决策清单
- 测试执行状态：本轮首轮只读，未执行

每个问题的判定结果和预计修改的文件类型（文档 / 代码 / 测试）必须写入首轮报告，供步骤 11 用户确认。步骤 10 问题清单必须包含本步骤独立发现的问题，不得仅列出步骤 2–9 的问题。

## 步骤 11：确认是否进入自动修复 loop

首轮报告输出后，向用户确认是否进入自动修复循环：

1. 明确回显本次的**终止标准**（默认「无高危+中危」，或用户在参数中指定的标准）与**将被自动修复的问题范围**（达到或高于该阈值的问题）。

   **达标硬规则（强制）**：默认"无高危+中危"必须同时满足**高危 = 0 且中危 = 0**，缺一不可。问题计数、问题清单、结论和修复范围四者必须一致；已有中危问题时**禁止**宣布达标或"无需修复"。

1b. 明确回显本次修复的**可改范围**（由步骤 0 的 phase 决定），例如：
   - 「当前 phase=`xf-detail`（设计阶段）→ 本次只会修改设计文档，不会改动任何代码；代码实现请走 `/xf-implement`」；
   - 「当前 phase=`xf-implement` → 本次可修改代码、测试和变更文档」；
   - 「无活跃 change → 本次可修改代码、测试和已有模块文档」。

2. **回显准备修改的真实文件清单**：按步骤 9A 的判定结果，逐条列出每个待修复问题预计修改的具体文件路径和修改类型（文档 / 代码 / 测试）。标记为「需人工决策」的问题**不出现在自动修复清单中**，单独列出提示用户自行处理。

3. 调用平台内置的 question 工具，让用户选择：
   - **A. 进入自动修复 loop（推荐）**：agent 按终止标准自动迭代修复，中途不再打断。
   - **B. 仅保留报告，不修复**：结束命令，维持只读结果。
   - **C. 我先手动处理**：结束命令，用户自行修改后可再次运行本命令。
3. 仅当用户选择 A 时进入步骤 12；否则结束命令。

## 步骤 12：自动修复 loop（最多 3 轮，中途不打断）

进入 loop 后**连续执行，轮次之间不再向用户确认**。硬上限 **3 轮**。每轮：

**① 修复**
- 针对当前问题清单中**达到或高于终止标准阈值**的问题（默认＝所有「高」「中」问题；低危不强制修），逐条修改对应文件。步骤 2–9 有充分证据的问题也可修复；步骤 9A 的三方问题必须先完成事实判定再修复，不得跳过判定直接改。
- **修复范围随 phase 收紧**（判据取步骤 0 的 phase）：
  - **有活跃 change 且 phase 早于 `xf-implement`（设计阶段）**：**只能修文档**——即 `xspec/xf/changes/` 下当前变更文档；**禁止改任何业务代码 / 测试**，也禁止改 `xspec/xf/modules/`、`xspec/xf/archive/`、`xspec/xf/changes/.gates/`。代码实现是后续 `/xf-implement` 的职责，本命令不得越阶段实现。
  - **有活跃 change 且 phase 为 `xf-implement`**：允许修正本次审计涉及的业务代码、测试和 `xspec/xf/changes/` 下当前变更文档；**禁止**改 `xspec/xf/modules/`、`xspec/xf/archive/`、`xspec/xf/changes/.gates/`。
  - **无活跃 change**：允许修正代码、测试和审计涉及的已有 `xspec/xf/modules/` 文档；仍**禁止**改 `xspec/xf/archive/`、`xspec/xf/changes/.gates/`；不得创建新模块或扩大模块职责。
- 记录本轮每一处改动（文件路径 + 改了什么）。

**② 复检**
- **重新真实执行步骤 2–9A 的全部检查**（不得凭记忆判断「已修复」），得到新的问题清单与各严重度计数。
- **若本轮改动了源码或测试**：必须**实际运行相关测试**（用项目真实的测试命令，如 `npm test` / `pytest` 等），把通过/失败/跳过数量记录下来供最终报告的 `▎验证结果` 使用。测试失败视为未修复，问题保留在清单中。

**③ 判定（按序）**
- **达标**：无高于终止标准阈值的问题 → loop 成功结束，进入最终报告。**达标硬规则（强制）**：默认"无高危+中危"必须同时满足**高危 = 0 且中危 = 0**，缺一不可。问题计数、问题清单、结论和修复范围四者必须一致；已有中危问题时**禁止**宣布达标或"无需修复"。
- **无进展**：本轮复检后，阈值内的问题数相比上一轮**没有下降** → 判为卡点，立即停止 loop（避免来回震荡/死循环），进入最终报告并标注卡点。
- **继续**：未达标、仍有进展且未到第 3 轮 → 进入下一轮。
- **触顶**：已完成第 3 轮仍未达标 → 停止，进入最终报告并列出剩余问题。

> ⚠️ 若某个高危修复涉及**改动需求范围 / 违背宪章**这类根本性变更，不要在 loop 里「就地打补丁」糊过去——在最终报告里**显著标注**，提示用户可能需要回退到 /xf-clarify 或 /xf-design 重做。

## 行为规则

- 本命令是流程外独立命令：不调用 `xf-enter-node`、`xf-set-phase`、`xf-validate`，不改变 phase，不执行审批或归档；
- **首轮审计只读**：步骤 0–10 不修改任何文件；只有用户在步骤 11 明确选择「进入自动修复」后，才允许在步骤 12 修改文件。
- **有活跃 change + 设计阶段（phase 早于 `xf-implement`）修复范围**：**只允许改 `xspec/xf/changes/` 下变更文档，禁止改业务代码和测试**；禁止改 `xspec/xf/modules/`、`archive/`、`.gates/`；
- **有活跃 change + `xf-implement` 阶段修复范围**：允许修正本次审计涉及的业务代码、测试和 `xspec/xf/changes/` 下当前变更文档；禁止修改 `xspec/xf/modules/`、`archive/`、`.gates/`；
- **无活跃 change 时修复范围**：允许修正代码、测试和审计涉及的已有 `modules` 文档；禁止改 `archive/`、`.gates/`；不创建新模块或扩大模块职责；
- 若 phase 为 `xf-archive`，立即停止，不执行任何操作；
- **loop 硬约束**：最多 3 轮；无进展立即停止；禁止无限循环。每轮复检必须真实重跑步骤 2–9A，不得凭记忆判定已修复。
- **步骤 9A 受 phase 门控**：只在「`xf-implement` 阶段」或「无活跃 change」时执行完整三方核对并允许改代码；设计阶段（phase 早于 `xf-implement`）不针对本轮新需求检查或修改实现，本轮尚未实施的需求不得判为实现缺陷——否则会架空 `/xf-implement` 并绕过阶段门禁。执行时发现代码与文档不一致，修复要落到实处，禁止只改文档假装一致。
- **改了代码必须跑测试**：loop 中任何一轮改动了源码或测试，复检时都要实际运行项目测试并把结果写入最终报告的 `▎验证结果`；测试失败即视为未修复。
- **终止标准来自用户**：默认「无高危+中危」，用户在 `$ARGUMENTS` 里可覆盖。
- 报告问题时给出具体位置（文件路径 + 章节）
- 不过度报警——信息项标为低
- 单端变更跳过前后端对齐检查
- 没有 research.md 正常跳过，不报为问题
- **单模块模式**：需求覆盖检查（步骤 2）仅检查该模块相关的 scope 功能点；跨模块检查（步骤 4/5/6）仅涉及该模块与其直接关联模块
- 所有输出使用中文
