# xf-split-v2：业务模块拆分

这是用户安装的独立拆分命令，与 `/xf-product-v2` 配套。命令版本 2.2.0。

## 运行范围

- 本命令不是正式 xflow 阶段节点，不调用 `xf-enter-node`，不修改 Flow、phase、审批记录、已有模块基线或现有命令。
- 产品输入/输出为 `xspec/xf/v2/PRODUCT.md`，自检证据为同目录 `split-review.md`。只写这两个独立稿路径；不替换正式 `xspec/xf/PRODUCT.md`、PRODUCT_DDD、ROADMAP 或现有 change。
- 读取 `.opencode/command-resources/product-split-v2/product.template.md` 和 `review-checklist.md`。正式 `/xf-split` 的检查结果不能替代本命令的 S01–S12 检查。
- 生成的是可评审的边界方案，不是代码、数据库迁移或部署指令，也不宣称已完成正式节点。采用该方案时需按原流程衔接。

## 用户输入

```text
$ARGUMENTS
```

接受拆分目标、范围约束、来源文件或方法偏好，例如“基于 DDD”“保持单体”“只调整计量与运行边界”。这些都是自然语言要求，不代表存在同名 CLI 参数。输入不拼接为 shell 命令。

## 职责分工

本命令把产品能力转化为有明确责任、数据所有权、协作契约和场景证据的逻辑模块。

负责 `模块结构`：业务过程、方法选择、方案取舍、模块列表、对象所有权、协作关系、业务规则落点、场景走读、设计交接、修订影响和拆分状态。

不擅自改写产品价值、用户场景、范围或会议结论。若发现这些输入有矛盾，记录具体受影响条目；可以补充有依据的业务澄清，但须标明来源和影响，不能为适配某个架构删除用户需求。

## 步骤 1：读取输入，识别现有系统

1. 读取独立 PRODUCT、相关来源和现有会话决定；修订时读取现有拆分依据版本和上次 split-review。
2. 若独立 PRODUCT 不存在且用户给了产品来源，或仓库已有 `xspec/xf/PRODUCT.md`，先按共享模板导入其业务内容为独立稿，并记录来源/版本。旧模块只作为现状证据，不直接当作本轮已验证结论。导入必须通过 P01–P08，结果一并写入 split-review。
3. 若既无可用产品输入也无足够场景，只整理已知内容并提出关键缺口；不从技术栈推造完整产品。
4. 仓库已有系统时，调查与本次场景有关的现有模块、写入方、控制面、接口和实现约束。区分当前实际边界、计划边界与外部不可控边界。
5. 一旦实际引用的业务内容发生变化，记录新的内容版本及澄清依据；不能把旧拆分版本改个日期就标为适配新需求。

若 `xspec/xf/v2/feedback.md` 存在，读取未关闭的设计/实现反例，核实其证据；受影响边界先标“需复核”，按步骤 3–7 重新分析。split-review 引用反馈 ID 和处理证据，供后续命令核实关闭；本命令不越权改写下游产物。

## 步骤 2：按业务复杂度选择方法

先说明复杂度来自哪里，再决定方法。用户明确要求 DDD 时采用 DDD；简单能力只作必要的战略建模，避免凑聚合和领域服务。

| 情况 | 采用方法 | 保留的检查 |
| :--- | :--- | :--- |
| 登记查询为主、业务规则少 | 按业务能力组织模块 | 场景、数据归属、更新权限和覆盖 |
| 多角色、多状态、资源/额度竞争、复杂授权 | 场景走读 + DDD 战略设计 | 统一语言、候选限界上下文、业务不变量、权威与协作 |
| 多源采集、转换、加工、消费为主 | 数据流与数据生命周期 | 来源、原始/派生、时效、质量、重放和消费职责 |
| 已有系统改造 | 在上述方法上增加现状与迁移分析 | 外部权威、兼容接口、唯一写入切换、退回条件 |

方法可以组合。不要将“前端、后端、数据库”作为默认业务拆分，也不要因为输入提到 DDD 就直接列出若干“XX 上下文”。

## 步骤 3：走读业务场景，再提出模块

沿 `SCN-xxx` 先识别发生的业务事实，再补触发它的请求、规则与后续反应；保留来源和未确定的因果关系，不先预设模块。

| 场景 / 步骤 | 角色与请求 | 读取的事实 | 要保护的规则 | 状态变化 / 结果 | 异常及现有处理者 |
| :--- | :--- | :--- | :--- | :--- | :--- |

至少走读核心成功路径与对边界影响最大的异常。按业务相关性选用并发、重复请求、超时、迟到、撤销、恢复、历史更正等情景，不为无关产品编造全部失败类型。

复杂流程或用户明确要求 EventStorming 时，必须读取 `.opencode/command-resources/product-split-v2/eventstorming.md` 并按其指引开展轻量过程建模：

1. 用已发生形式列事件，补命令、角色/外部系统、决策信息、不变量及反应规则。区分命令受理与业务目标达成。
2. 标明因果、分支、并行和时间触发；不把并发业务强排为单一顺序。
3. 将争议和缺证据的 Hot Spots 关联 Q，说明影响与当前行为；AI 推演、材料已知和业务方确认分别标识。
4. 从正常与异常流程提取“前提—动作—预期结果”的验收例草案，再推导边界。

业务过程摘要写入 PRODUCT，详细变体与证据写入 split-review。简单场景用自然语言即可，不强填所有标记。业务事件不自动等于跨模块集成事件；本方法不要求消息队列或事件溯源，也不能冒称举行了真实工作坊。

## 步骤 4：建立语义与所有权草案

先对核心对象分清主数据、配置意图、实际观测、资源/权限承诺、历史事件、派生结论。更新频率仅作辅助，不据此机械拆模块。

逐项回答：

1. 这个事实具体表达什么？是否与另一个同名“状态”含义不同？
2. 外部权威来源是谁？内部谁解释与维护这项语义？
3. 谁允许提出修改？哪条权威路径接受修改？
4. 哪些规则需要一起保护？哪些视图允许延迟、复制或重建？
5. 名称/版本/时间变化后如何关联？来源冲突或结果未知由谁裁决？

同一实体可在不同上下文中有不同模型，但同一语义事实不能存在两个独立权威写入方。读模型可以组合多域信息；来源清楚、可重建的投影不视为重复主数据。

## 步骤 5：形成候选边界与取舍

按业务语言、共同保护的规则、生命周期、修改权限和变化原因形成候选模块。

采用 DDD 时：

- 识别核心域、支撑域和通用能力，说明依据；不要把每块都标为核心域。
- 定义候选限界上下文及内部统一语言，说明哪些同名对象在边界两侧含义不同。
- 明确上下文与实现模块的映射：一个上下文可以有多个模块，模块也不等于微服务。
- 指出关键一致性边界及需要设计阶段验证的实现约束，但不在本阶段生成完整实体类、聚合结构、Repository、DDL 或锁方案。
- 保留现有系统的权威边界，必要时用适配/翻译契约隔离外部语义；不能通过再建本地表宣称取得控制权。

有真实取舍时给出 2–3 个候选方案。比较边界、能力覆盖、跨模块协调、现有能力复用、变化成本与风险；不能用“单体/微服务”替代逻辑边界方案，也不能仅改名字凑第二套。

无实质性替代方案时说明为何采用最小方案。用户已有明确选型或授权时直接执行；确有业务取舍未定时，先把方案做具体，再提出一个聚焦的问题。可逆草案可标“建议采用”，不得假称“用户已选定”。

## 步骤 6：定义模块、所有权与契约

### 模块列表

每个模块包含：稳定 slug、中文名、业务职责、明确排除项、关联 CAP、对外能力、模板类型与拆分状态。状态使用“候选 / 场景走读通过（设计待验证）/ 需复核”；实现进度另据代码和验收证据记录。旧稿的“边界已验证”迁移为与证据相符的状态，不能继承为最终设计结论。

如项目使用 xflow 模板类型，读取当前 CATALOG；类型服务于制品选择，不能反过来决定业务边界。未注册类型明确其适配影响，不擅自把数据管线改成后端只为获得某份模板。

### 核心对象所有权

每行描述同一语义事实，至少包含外部来源、内部所有者、修改入口、消费者、版本/时效和一致性规则。派生结果必须有计算与更正责任方；不能因为“跨域”就让核算、分配等结果失去归属。

### 模块依赖关系

分别描述：

- 查询：谁提供哪种只读事实/投影，附哪些版本与质量信息；
- 命令：谁接受哪种业务变更，成功/拒绝/未知分别意味着什么；
- 事件：谁发布哪项事实、谁消费、谁负责去重/迟到/失败恢复；
- 外部关系：哪个能力由现有系统权威提供，适配方承担哪些翻译职责。

图中的每类边都应有明确含义，不能把调用方向、数据流向和代码 import 混在一张无标签图里。逻辑调用若形成环，检查是否需要协调者、接口反转或重划边界；业务反馈流可以闭环，但仍须登记全部契约与消费责任。

本阶段验证逻辑接口依赖及业务协作。除非实际检查了代码，不写“代码依赖已无环”；不能以“事件不计入依赖”为由掩盖模块之间的耦合。

## 步骤 7：用规则与场景检验边界

对每个 `BR-xxx` 指定责任模块、协作者、约束的对象及违反后的处置。再逐个回放已选场景，确认成功、失败与恢复时均有明确责任。

必须识别以下失败信号：

- 两个模块都能独立改变同一个权威事实；
- 一个不变量需要多个模块各自读取旧快照再写入，却没有明确仲裁契约；
- 期望、观测、承诺由同一个“状态”字段代表；
- 统计/核算结果没有计算与修正责任方；
- 外部控制面可绕开本地约束，但文档宣称“唯一入口”；
- 一个简单业务修改总需要同步改多块，却没有说明保留拆分的价值；
- 把一个对象、表或事件机械拆成一个模块，或把所有关联对象塞进一个大模块。

发现问题就调整候选边界并重跑受影响场景；不能只增加注释来保留原方案。

技术实现未知但会决定边界是否可行时，查证现有契约或做有边界的研究。外部业务权限/规则需要用户提供时，保留具体问题与保守路径；该部分只能是候选，不能标为已验证。

填写设计交接：关联 SCN / CAP / BR、权威事实与关键协作，列明 design 需要验证的聚合/一致性边界假设、detail 需精化的契约和异常验收例，以及使边界需要回看的条件。这是后续设计的明确输入，不是把当前已影响方案可行性的技术疑问推迟到实现阶段。

## 步骤 8：修订影响与写入

首次拆分直接填入共享模板的模块部分，并替换各小节“本轮只定义产品”的未拆分说明，按实际证据更新拆分状态。已有拆分时还需提供旧 → 新映射，包括 CAP、对象、写入方、契约、已知数据/代码/设计/任务影响及兼容/切换条件；本命令只记录影响，不执行迁移。

保留模块 slug 的稳定性，不为措辞变化重命名；若有真正拆分/合并，明确旧 ID 的去向。业务概念未变、拆分结论未变时幂等返回，不制造新版本。

记录：本次方法、建议/已选择方案、产品内容版本、拆分依据版本、设计/现状证据基线、拆分状态、实际用户决定依据和关键假设。业务输入更新后，旧拆分证据不能继续标为适配新版本。即便业务版本不变，若新设计证据或场景反例否定原有所有权、一致性或恢复假设，也要将受影响边界标为“需复核”，回到步骤 3–7；不能靠保持需求版本掩盖失效结论。

只更新独立 PRODUCT 的模块部分、必要且有依据的业务澄清及版本信息。架构图以表达关键关系为准，不强制所有产品生成多张图或独立 HTML。

## 步骤 9：证据自检与完成报告

重新读盘执行共享清单 S01–S12，将结果写入 `xspec/xf/v2/split-review.md`。记录被检查文件的内容摘要、日期、引用证据、逐条结论、实际走读场景和仍未确认的假设；发生业务内容导入/修订时一并执行 P01–P08。

机械检查只能证明结构、引用与覆盖；语义结论必须说明具体来源、规则和场景如何支持它。检查失败先修复能自主修复的部分，复查受影响条目。

完成时报告：

- 独立 PRODUCT 和 split-review 的路径；
- 使用的方法与选择理由；
- 主要职责变化、数据所有者和关键协作；
- 已走读的边界情景、仍属候选的结论和设计交接项；
- 现有制品迁移影响；
- 可交接到 `/xf-brainstorm-v2` 或 `/xf-clarify-v2` 的范围；两个入口二选一，按共享下游约定继续；
- 本次没有替换正式 PRODUCT、变更状态或实施基线。

不能以模块数、DDD 术语数量、没有多个“并且”或一张无环图作为正确性证明；不能把独立拆分报告称为正式 `/xf-split` 已通过。
