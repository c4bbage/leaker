## 步骤 2.5：设计测试用例

从 task.md + spec + design 中提炼所有可验证的测试用例，写入对应模块的 spec 文档（`spec.md` 或 `spec.delta.md`）的「验收测试」章节。

**不含**：集成测试（走 integration.md）、最终全量验证（走步骤 5）。

### 执行步骤

1. 遍历步骤 2b 确定范围内的任务，为每个任务点设计 1~N 个测试用例
2. 在对应模块的 spec 文档末尾追加（或更新）「验收测试」章节
3. 每个测试用例写明：关联任务编号、测试目标、具体断言条件

### 写入格式

在 spec 文档中追加：

```markdown
## 验收测试

### T001 - 问卷创建

| # | 路径 | 断言 |
|---|------|------|
| 1 | 正向 | `createSurvey({title:'测试'})` 返回对象，`title === '测试'`，`id` 为 UUID |
| 2 | 负向 | `createSurvey({})` 抛出 ValidationError，message 含 'title' |
| 3 | 边界 | `createSurvey({title:''})` 抛出 ValidationError |

### T002 - 问卷分页查询

| # | 路径 | 断言 |
|---|------|------|
| 1 | 正向 | `findByPage(1, 10)` 返回 `{list, total}`，list.length <= 10 |
| 2 | 负向 | `findByPage(0)` 抛出 RangeError |
| 3 | 边界 | `findByPage(999999)` 返回空 list，total 不变 |
```

### 设计原则

- 每个任务至少覆盖**正向 + 负向**两条路径
- 断言必须具体（期望返回值、期望异常、期望字段），不能只写"功能正常"
- 粒度在此步骤确定，进入 TDD 循环后不再修改测试设计
- 测试用例是实现的唯一驱动力：没有对应用例的代码不写

## 步骤 3：TDD 循环实现

**加载并遵循 skill `test-driven-development`（`skills/test-driven-development/SKILL.md`）**。

### 核心循环

对步骤 2.5 中的每个测试用例，严格按红-绿-重构执行：

```
对每个测试用例：
  1. 红：在测试文件中写出该用例的测试代码
  2. 验证红：运行测试，确认它因功能缺失而失败（不是语法错误）
  3. 绿：写最少的生产代码让这个测试通过
  4. 验证绿：运行测试，确认通过且未破坏其他测试
  5. 重构：在全部绿色的前提下清理代码
  6. 下一个用例
```

### 测试文件组织

- 按模块/功能域组织测试文件（如 `survey-crud.test.ts`、`collect-service.test.ts`），一个文件包含该模块下多个用例
- 测试文件放在项目约定的测试目录中（`tests/`、`__tests__/`、`test/` 等，跟随项目已有结构）
- 同一模块的用例批量运行验证

### 设计对照（实现每一项时检查）

- 实现是否符合 spec 的功能描述
- 接口是否符合 contracts 定义
- 数据操作是否符合 data-model 定义
- 代码风格是否符合项目约定和宪章要求

### 节奏控制

- 每完成一个模块（或一组相关用例）后，跑一次 lint + typecheck（仅检查本批变更涉及的文件）
- 每完成一个模块后，全量回归：运行该模块所有已有测试
- 同一用例修复 2 次仍未通过 → 暂停，记录原因，向用户报告后跳过，进入下一项

### 异常处理

- 设计文档与实际冲突 → 暂停，说明冲突点，给出 1 个推荐方案 + 最多 2 个备选，等用户决策
- 需要额外技术决策 → 暂停，描述问题，给出推荐方案并说明理由，最多列 3 个选项，等用户拍板
- 依赖未满足 → 暂停并说明；如依赖在同模块内可调整顺序，否则等用户决策

### 阶段性报告（循环结束后输出）

```
📊 TDD 循环完成

✅ 已通过：N 个用例
⏭️ 跳过：M 个（列出任务编号 + 原因）
📦 本次开发内容：{概括}
```

## 实现原则

1. **遵守宪章**：核心原则和技术方向以 constitution.md 为最高准则
2. **忠于设计**：严格遵循设计文档，不自行扩展功能
3. **测试驱动**：没有对应用例的代码不写；先看到测试失败，再写实现
4. **最小实现**：只写让当前测试通过的最少代码，不预设未来需求
5. **及时沟通**：遇到问题暂停而非猜测
6. **不碰 SoT**：只修改 `xspec/xf/changes/` 目录和项目源码，不修改 `xspec/xf/modules/`
7. **代码可运行**：每批完成后确保无 lint 错误和类型错误

## 行为规则

- 按 spec 中验收测试的顺序逐项执行，不跳项
- 进入 TDD 循环后禁止修改 spec 中的测试设计（断言条件）
- 先写了实现再补测试 → 删掉实现，从测试重来
- 遇到设计偏差暂停沟通
- 不修改 `xspec/xf/modules/` 目录
- 所有交互使用中文

## 完成后验证

完成以上任务后，运行结构化验证：

```bash
node .xflow/scripts/xf-validate.mjs --node xf-implement --flow xf
```

该脚本返回 JSON，包含**两类检查，都必须处理**：

1. **机械检查**（脚本自动判定，看 `pass` / `mechanical[]`）：
   - `pass: false`（exit≠0）→ 按 `mechanical[]` 中每条 `fail` 的 `detail` 修复（补齐缺失文件、清除占位符、补章节等），然后**重新运行脚本**，直到通过。

2. **语义检查**（脚本**不自动判定**，`semantic[]` 是交给你亲自执行的清单）。这一步最容易走过场，因此有**硬性取证要求：没有过程依据的 PASS 一律无效**。对 `semantic[]` 中**每一条**，按下述三步执行并留痕：

   a. **验证时重新读盘**：对该规则涉及的产物文件（及其依赖的上游制品）**当场重新 Read 一遍**，**不得**凭"刚才生成的内容"或对话记忆判断——文件可能在生成后被改动或删除，只有此刻磁盘上的内容算数。
   b. **摘录取证**：从刚读到的内容里**摘一小段原文**（加引号，标明「文件路径 # 章节/行」）作为依据；需要跨文件对照的规则，涉及的**每个文件都要摘**。
   c. **对照判定**：拿摘录去比对该条 `fail_condition`，得出 PASS/FAIL 并说明为什么。

   若某条 `fail_condition` 属于"某文件/产物必须存在"一类：一律以**当场读盘 / 列目录的实际输出**为准并把结果贴出来，禁止凭记忆或"刚生成过"下结论；判定涉及的清单（如受影响模块名）从其事实源（如 `change.yaml`）**现取**，不凭记忆。**具体查哪些文件、按什么标准，完全以该条 `fail_condition` 的描述为准**——这些由 Flow 配置（web 侧语义检查）定义；本 wrapper 通用于所有 Flow，不预设任何目录结构。

   逐条按此格式输出（**缺「依据」栏即视为 FAIL**）：
   ```
   [PASS/FAIL] <name>
     依据：读取 <文件路径>#<章节/行>，见「<原文摘录>」（存在性类：贴 ls/Read 的实际结果）
     结论：<对照 fail_condition，为什么满足 / 不满足>
   ```

   任一条 FAIL → **立即修复产物**，然后**重新读盘复核该条**（若牵动机械检查，一并重跑脚本），直到带依据判为 PASS。
   > 有些节点的产出路径无法预先声明（如拆分阶段模块名运行时才定），这类正确性**只能靠语义检查**保证，因此 `semantic[]` 不可跳过。

**仅当机械检查 `pass: true` 且 `semantic[]` 每条都带「依据 + 结论」判为 PASS 时，才可告知用户"节点已完成"。** 只写结论、给不出原文摘录的 PASS 无效，必须补取证或改判 FAIL。任一未过：把验证报告原文 + 你的逐条取证判定展示给用户，修复后重来，**不得跳过语义检查、也不得无依据直接报完成**。

随后对本节点制品再跑一次质量检查（**检测即止 · 不作为本节点完成门禁**；结果写入 `~/.xflow`，由 Web 端展示并作为人工审批依据）：

```bash
node .xflow/scripts/xf-quality.mjs --node xf-implement --flow xf --l1-only
```

`rules[]` 结果逐条 `[PASS/FAIL] <rule> <name>` 如实列入完成报告（`l1_fail` 不得隐瞒）。**对 FAIL/阻断项，主 agent 必须当场修复产物并重跑复核，不得只报告不处理**；确实无法修复的，如实列明原因并提示用户。`need_judge` 语义项由主 agent **调用 subagent** 按输出中的 evidence 当场判定 `PASS/FAIL + 逐字依据`。
