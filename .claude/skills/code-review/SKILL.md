# 代码审查

对本次实现的改动做两轴审查：

- **Standards** — 代码是否符合本项目的编码规范？
- **Spec** — 代码是否忠实实现了 task.md / spec / 设计文档的要求？

两轴作为**并行子 agent** 运行，彼此不污染上下文，然后由本 skill 聚合它们的发现。

## 流程

### 1. 确定审查范围

确定本次实现改动了哪些文件。优先用 git 拿到客观 diff：

- 有可用基线（分支起点、上一个 commit 等）→ `git diff <基线>...HEAD`（三点，对 merge-base 比较），并记下 `git log <基线>..HEAD --oneline` 的提交列表
- 改动尚未提交 → 用本次 implement 实际触碰的文件清单作为审查范围

继续之前，确认范围非空。空范围应在此处失败，而不是进两个并行子 agent 之后才发现。

### 2. 确定 Spec 来源

按顺序找本次改动的需求来源：

1. 对应模块的 `task.md`（任务清单）
2. `spec.md` / `spec.delta.md`（功能范围和验收标准）
3. `design.md` / `design.delta.md`、`contracts.md`、`data-model.md`（设计约束）

都找不到 → 问用户 spec 在哪。用户说没有 → Spec 子 agent 跳过，报告"无可用 spec"。

### 3. 确定 Standards 来源 + 异味基线

读取本项目记录编码方式的文件：首先是 `xspec/xf/constitution.md`（最高准则），其次是项目已有的代码约定（命名、目录结构、导入、错误处理模式）。

在项目记录的规范之上，Standards 轴始终携带下面的**异味基线**——一套固定的 Fowler 代码异味（《重构》第 3 章），即使项目什么都没记录也适用。两条规则约束它：

- **项目规范优先**：项目明确认可的写法，即使基线会标记，也压制该异味。
- **始终是判断而非违规**：每个异味是带标签的启发式（"可能的 Feature Envy"），不是硬违规；工具已强制检查的项跳过。

每个异味按「是什么 → 怎么修」对照改动：

- **Mysterious Name（费解的命名）** — 函数、变量、类型的名字没揭示它做什么或装什么。→ 重命名；想不出诚实的名字，说明设计本身模糊。
- **Duplicated Code（重复代码）** — 同一逻辑形状出现在多处。→ 提取共享形状，两处都调用它。
- **Feature Envy（依恋情结）** — 一个方法伸手进另一个对象的数据，多过自己的数据。→ 把方法移到它依恋的数据上。
- **Data Clumps（数据泥团）** — 同样的几个字段/参数总是一起出现（一个想出生的类型）。→ 打包成一个类型传递。
- **Primitive Obsession（基本类型偏执）** — 用原始类型/字符串代替本该有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **Repeated Switches（重复的 switch）** — 同一个 switch/if 级联在改动中反复出现。→ 用多态，或两处共享的一个 map 替代。
- **Shotgun Surgery（霰弹式修改）** — 一个逻辑变更迫使在多个文件分散编辑。→ 把一起变化的东西收进一个模块。
- **Divergent Change（发散式变化）** — 一个文件/模块因几个不相关的原因被修改。→ 拆分，让每个模块只因一个原因变化。
- **Speculative Generality（投机性泛化）** — 为 spec 没有的需求添加的抽象、参数、钩子。→ 删掉；内联回去，直到出现真实需求。
- **Message Chains（过长的消息链）** — 调用方不该依赖的 `a.b().c().d()` 长导航。→ 把这段行走藏到第一个对象的一个方法后面。
- **Middle Man（中间人）** — 一个类/函数主要只是转发给别人。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）** — 子类忽略或覆盖了继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行派生两个子 agent

在一条消息里发两个子 agent 调用，两个都用通用子 agent。

**Standards 子 agent prompt** 包含：

- 完整的 diff 命令（或改动文件清单）和提交列表
- 步骤 3 找到的规范来源文件清单，**外加完整粘贴步骤 3 的异味基线**——子 agent 没有别的途径拿到它
- 简报："逐文件 / 逐处报告 (a) 每处违反项目规范的地方：引用规范（文件 + 规则）；(b) 发现的每个基线异味：点名并引用代码片段。区分硬违规和判断项——违反项目规范可以是硬的，基线异味始终是判断项，且项目规范优先于基线。跳过工具已强制的项。400 字以内。"

**Spec 子 agent prompt** 包含：

- diff 命令（或改动文件清单）和提交列表
- spec 的路径或内容
- 简报："报告：(a) spec 要求但缺失或部分实现的需求；(b) 改动中 spec 没要求的行为（范围蔓延）；(c) 看起来实现了、但实现方式看起来不对的需求。每条发现引用对应的 spec / task 行。400 字以内。"

spec 缺失时跳过 Spec 子 agent，在最终报告里注明。

### 5. 聚合

把两份报告分别放在 `## Standards` 和 `## Spec` 标题下，原样或轻度清理。**不要**合并或重新排序发现——两轴刻意分开（见「为什么是两轴」）。

结尾一行总结：每轴发现总数，以及每轴内最严重的问题（如有）。不在两轴之间挑单一赢家——那正是要避免的重新排序。

任何一轴有硬问题 → 回去修，修完重新验证，再审查。两轴都干净才算审查通过。

## 为什么是两轴

一个改动可能一轴过、另一轴不过：

- 符合所有规范但实现了错的东西 → **Standards 过，Spec 挂**
- 完全实现了需求但破坏了项目约定 → **Spec 过，Standards 挂**

分开报告，避免一轴掩盖另一轴。
